Subagent 与 Team Runtime：从 Codex、Claude Code、OpenClaw、Hermes 到开源多智能体系统

Subagent 不是“多叫几次模型”。真正的问题是：当一个主 agent 把工作交给另一个 agent 时，谁拥有上下文、谁能使用工具、谁负责调度、谁验证结果、失败以后谁恢复。只要这些边界没有被 runtime 明确下来，多智能体就会退化成一组更贵、更难审计、更容易互相污染的 prompt。

本文把 subagent/team 技术放在一个工程坐标系里讲：先用 Codex、Claude Code、OpenClaw、Hermes 四条主线拆开产品级和源码级实践，再把 LangGraph、CrewAI、OpenAI Agents SDK、Google ADK、Microsoft Agent Framework、AutoGen/AG2、CAMEL、MetaGPT、Strands 等开源实现放到同一个排序表里比较。排序分两层：第一层按 GitHub 热度，第二层按本文定义的 team runtime 能力。

写作快照源码、文档和 GitHub stars 快照时间为 2026-06-16。后续版本可能改变 API、stars 和项目定位。
公共证据边界Codex、OpenClaw、Hermes 使用固定 commit 的 GitHub 源码锚点；Claude Code 使用 Anthropic 官方公开文档，不把未公开实现细节写成源码事实。
排序口径stars 只代表注意力；能力排序看隔离、拓扑、上下文、并发、恢复、安全和可观测性。

一、先给定义：subagent 是边界，team 是拓扑

如果把 agent 看成“能读上下文、调用工具、产出行动建议的运行体”，那么 subagent 就是由另一个 agent 或 runtime 派生出来的受限运行体。它可能有自己的上下文窗口、系统提示、工具权限、工作目录、会话历史和终止条件。它的输出通常应该是证据、补丁、报告或候选结论，而不是直接覆盖父级的最终决定。

Team runtime 则是多个 agent 之间的编排拓扑。它回答的问题不是“有没有子 agent”，而是“这些 agent 如何协作”：是主 agent 把任务 handoff 给专家，还是 supervisor 分派给 worker，还是一组 agent 共享 group chat，还是显式图工作流，还是由持久队列/看板调度长任务。拓扑一变，失败模式也会变。

1.1 七个能力维度

本文的能力排序不是按 marketing 口径，也不是按某个 demo 是否炫。一个真正可落地的 subagent/team runtime 至少要回答七个问题。

维度要回答的问题低成熟度表现高成熟度表现
隔离边界子 agent 能看到什么、能改什么、能调用什么？直接复制完整聊天和全部工具。独立上下文、scoped tools、独立权限、必要时单独 workspace 或 sandbox。
编排拓扑谁派活，谁等待，谁合并？只有“让另一个模型回答一下”。handoff、supervisor、graph、durable queue 等拓扑明确。
上下文纪律父子之间传多少历史，结果如何返回？盲目 fork 全历史，token 成本和污染一起放大。默认 brief，必要时 fork；子结果作为 evidence/report 返回。
并发与背压能否并行、等待、取消、限流？并行 spawn 后靠人工猜测完成状态。有 wait/yield、timeout、max concurrency、queue depth 和取消传播。
持久化与恢复进程重启、长任务、失败后怎么办？内存里跑完就算，丢了就丢。任务表、checkpoint、resume、stale recovery、tombstone 或人工接管路径。
安全治理子 agent 是否能越权写文件、联网、读 secrets？父级有什么权限，子级就有什么权限。deny/allow、approval、sandbox、human-in-loop、输出验证。
可观测性能不能追踪谁做了什么？只看到最后一段自然语言。事件流、trace、hook、transcript、task id、parent/child correlation。

1.2 为什么“更多 agent”经常变差

Subagent 的收益来自分治：更小的上下文、更明确的角色、更少的工具权限、更好的并行性。它的风险也来自分治：父级可能把责任甩给子级，子级可能缺上下文，多个子级可能重复工作，长任务可能没有恢复点，工具权限可能被复制得过宽。

所以判断一个系统好不好，不能只看能不能 spawn。要看它有没有让父级保持 ownership。一个高质量设计通常会把子结果降级为“证据”，父级仍然负责核验、合并和交付。Codex 的多 agent 描述里明确把 child output 放在 parent synthesis 之前；OpenClaw 的 subagent 文档也强调 child output 是 report/evidence，不是用户指令；Hermes 的 Kanban completion 要求结构化 handoff；Claude Code 的官方 subagent contract 也把结果返回主 agent 处理。

二、四条主线：从产品契约到运行时边界

2.1 Codex：thread tree、mailbox 与可观测的协作事件

Codex 的多 agent 设计非常值得细读，因为它不是只给模型一个“你可以找助手”的提示，而是把协作做成一组工具、协议事件和 UI 可见 item。固定到 commit 02dce8e 看，工具规格在 multi_agents_spec.rs 的 v2 spawn_agent里要求 task_name 和 message，并在 v2 描述里定义 canonical task path，例如 /root/task1/task_3。这件事很小，却决定了后续能否 list、wait、resume 和向指定子任务发送 follow-up。

spawn.rs 先解析 fork mode、role 和模型 override，随后在 构造 child thread metadata时把 parent thread、environment、fork mode 和初始 inter-agent message 绑定进去。它还会在 spawn 后发出 SubAgentActivityEvent，让 UI 和 tracing 能看到子任务开始，而不是只在自然语言里宣布“我开了一个子任务”。

上下文继承要特别小心：在这版源码里，fork_turns 不传时默认 all，也就是子线程继承完整父历史；如果要让子任务从干净上下文开始，需要显式传 none。这解释了为什么 subagent 不是自动安全边界：隔离必须由 runtime 默认、调用参数和任务 brief 一起决定。

Codex 的关键设计不是并行，而是 mailbox 纪律

Codex 把“给子 agent 留消息”和“触发子 agent 继续跑”拆开。send_message 使用 queue-only delivery，只把消息放进子 agent 的 mailbox；followup_task 则使用 trigger-turn delivery，让子 agent 实际开始下一轮。这个拆分非常工程化：父级可以在不打断子线程的情况下追加上下文，也可以明确触发下一轮执行。

等待也不是靠轮询自然语言。wait_agent 处理 timeout、订阅 input queue activity，并发出 CollabWaitingBegin；结束时在 CollabWaitingEnd 里交代等待结果。底层等待结果可能是 mailbox activity、被 steering 或 timed out，见 wait_for_activity。这让“父级什么时候卡住、卡在哪里、为什么恢复”变成协议事实。

父级合成，不是子级盖章

Codex 还把 child terminal turn 变成父级可见的 inter-agent communication。maybe_notify_parent_of_terminal_turn 检测子线程 final status，再通过 inter-agent communication 把完成信息转给父级。App protocol 侧也有 CollabAgentToolCall 和 SubAgentActivity，说明它不是 CLI 私有小技巧，而是 UI 层能表达的协作模型。

Codex 的强项是：thread tree、fork policy、mailbox、wait、event stream 和 UI item 都在同一个 runtime 里。它的限制也来自这里：这是 Codex 产品/runtime 内部能力，不是一个通用 Python/JS 框架。你能学到的是边界设计，而不一定能直接把这套工具名搬到自己的服务里。

2.2 Claude Code：公开契约优先的 specialist subagent

Claude Code 的公开文档把 subagent 讲成“专用 AI subagent”，重点是任务特化和上下文管理。Subagents 文档说明每个 subagent 可以有自己的 context window、custom system prompt、specific tools 和独立权限；Agent SDK 的 subagents 文档则把它描述为主 agent 可 spawn 的独立 agent instance，用于隔离上下文、并行分析和专用指令。这里的公共契约是“定义专家，然后由主 agent 在合适任务上调用”。

这个模型和 Codex 的 thread tree 有一个重要区别：Claude Code 面向用户暴露的是专家 contract，而不是完整的 inter-agent mailbox 协议。你可以把 researcher、reviewer、tester、doc writer 这类角色沉淀成项目或用户级定义；主 agent 在需要时调用它们，拿回报告，再自己合成最终回答。官方 hooks 文档还提供 SubagentStart 和 SubagentStop 事件，后者能带上 agent_id、agent_type、agent_transcript_path 等元数据，这让 subagent lifecycle 可以进入审计和自动化。

Claude Code 的优势：角色库和上下文隔离

如果你的问题是“我希望每个仓库都有自己的 code reviewer、security auditor、docs maintainer，而且这些角色不要污染主上下文”，Claude Code 的 subagent contract 很自然。它把角色描述、工具范围和模型选择放在定义面上，运行时由主 agent 选择合适的专家。这种 contract 很适合团队维护，因为它接近“技能说明书”：什么时候用、看什么文件、能用哪些工具、返回什么格式。

Claude Code 的边界：公开文档不等于完整 runtime 规格

公开文档没有把内部调度、背压、长任务恢复和 UI 协议展开到 Codex 源码那种粒度。因此本文不把 Claude Code 排成“最强 runtime 源码样本”，而把它视为“最成熟的产品级 specialist subagent contract”之一。它的可迁移经验是：subagent 定义应该像 contract，而不是一句临时 prompt；结果应该回到父级验证，而不是直接替代父级。

2.3 OpenClaw：Gateway 里的 session-spawn 与多通道隔离

OpenClaw 的定位更像“always-on agent gateway”。它的 README 把 Local-first Gateway、多 channel inbox、多 agent routing、isolated agents、workspace/session 和 tools 放在一起。多 agent 不是只有 prompt 编排，而是和 channel account、agent workspace、auth profile、session store 绑定在同一套 Gateway 架构里。

OpenClaw 的 multi-agent routing 文档把一个 agent 定义成带 workspace、state directory、session history 和 auth profile 的完整 persona；同一 Gateway 可以承载多个互相隔离的 agent，见 多 agent 隔离说明。这让它的 subagent 设计天然带有“会话隔离”和“路由回送”的味道。

sessions_spawn 是非阻塞的 background run

Sub-agents 文档把 subagent 定义为从现有 agent run 派生出来的 background agent run，运行在形如 agent:<agentId>:subagent:<uuid> 的独立 session。它的主要目标包括并行慢任务、默认隔离、避免滥用 session tools，以及支持可配置 nesting depth。

具体工具上，sessions_spawn默认创建隔离 session，并立即返回 runId 和 childSessionKey。native subagent 的 delegated task 会进入子 session 第一条可见 [Subagent Task] 消息；system prompt 只携带 runtime rules 和 routing context。spawn behavior则强调非阻塞和 push-based completion：父级如果需要等结果，应该 sessions_yield，不要轮询。

OpenClaw 的独特价值：channel、thread、ACP 与 sandbox

OpenClaw 不只是本地编排库。它关心“结果怎么回到 requester chat channel”。completion delivery会尝试唤醒或 steer requester run，失败时通过 handoff/queue 路由补救。它还支持 native subagent 和 ACP runtime 两条路径，可以把 Claude Code、Gemini CLI、OpenCode 等外部 harness 放进同一个 Gateway 模型里。

安全和资源方面，OpenClaw 的 subagent 文档提供 concurrency、liveness、recovery 和 limitations：subagent lane 默认有 max concurrency，stale run 不会永远算 active，restart recovery 有边界，sessions_spawn 总是非阻塞，maximum nesting depth 默认受限。任务 registry 也把 subagent、acp、cli、cron 明确成 runtime 枚举，见 TaskRuntime。

OpenClaw 的能力强在运行平面：多通道、线程绑定、Gateway 路由、session store、sandbox、ACP bridge 和 delivery policy。它的限制也很明确：如果你只想在一个 Python 服务里写复杂状态图，OpenClaw 可能太平台化；但如果你的目标是“一个 AI 助手长期生活在多个消息渠道里，还能把长任务派给隔离子会话”，它是非常接近真实生产形态的样本。

2.4 Hermes Agent：delegate_task 与 Kanban operating plane

Hermes 的 subagent/team 设计有两条线：一条是 delegate_task 这种同步或批量 delegation；另一条是 Kanban board 这种持久任务平面。delegate_tool.py 的 docstring直接说明：它会 spawn child AIAgent，使用隔离上下文、受限 toolsets、独立 terminal sessions，父级只看到 summary。这个定位很清楚：子 agent 是工作隔离体，不是共享记忆里的另一个人格。

它还非常重视滥用边界。DELEGATE_BLOCKED_TOOLS 默认阻止子 agent 再使用 delegate_task、memory、send_message、execute_code 等工具；并发和深度默认值控制 fanout 规模；spawn depth 逻辑还把普通 delegation 和 orchestrator role 区分开。换句话说，Hermes 没有把“子 agent 可以继续无限生子”当默认能力。

child agent 的构造：继承、裁剪、再加身份

Hermes 在构造 child agent 时会处理 provider/model/toolset 的继承和覆盖。toolset inheritance会做 intersection/override，并且只在 orchestrator role 下重新开放 delegation；child AIAgent 创建会设置 skip_context_files=True、skip_memory=True、platform="subagent"、parent_session_id 和独立 iteration budget；随后 写入 depth、role、subagent id 和 hooks。这类细节说明 Hermes 的 delegation 是工程对象，不是字符串拼接。

Kanban 是 Hermes 的 durable team runtime

Hermes 的 Kanban 工具把 team runtime 推到更重的一层。kanban_tools.py 的说明强调这些是给 dispatcher workers 和 orchestrator profiles 用的结构化工具，不是让 worker shell 到数据库里乱改。ownership guard防止 worker 修改非自己任务；kanban_complete要求带 summary、result、metadata 和 artifacts，保证 handoff 是结构化的。

调度层在 kanban_watchers.py 里以 gateway-hosted watcher 运行，按 board 调用 dispatcher；max_spawn、max_in_progress、failure_limit、stale timeout 和 per-profile limit提供背压；每个 board 的 dispatch_once把队列执行变成可恢复循环。观测上，observability 文档提供 session、task、parent/child correlation id；subagent hooks则把 start/stop 事件纳入 trace。

Hermes 的强项是 operational discipline：隔离、受限工具、并发、深度、hooks、Kanban、ownership、structured handoff、dispatcher backpressure 都比较完整。它的代价是系统复杂度更高，更像“团队操作系统”而不是轻量 SDK。

四、按能力排序：谁更像真正的 team runtime

能力排序必须先说口径。本文不是评“谁最会写 demo”，而是评“当任务变长、工具有风险、多个 agent 并发、需要恢复和审计时，runtime 给了多少可靠边界”。因此产品级系统、平台型系统和 SDK 会混在一起比较，但每一行都会说明适用边界。

这里不做机械总分相加，因为不同系统的目标不同：Codex 和 Claude Code 是产品内 subagent runtime，LangGraph、CrewAI、OpenAI Agents SDK、Microsoft Agent Framework 更像通用 SDK，OpenClaw 和 Hermes 更像 operating plane。本文的 tie-breaker 是：优先看是否有完整的 parent-child 闭环，其次看拓扑表达与恢复能力，再看安全隔离、可观测性和公开证据深度。也就是说，一个通用图框架可能在 workflow 上更强，但如果它把权限、sandbox 或 delivery 留给应用层，本文不会把它简单排到所有产品级 runtime 前面。

6Microsoft Agent Framework微软新路线，支持 sequential、concurrent、handoff、group chat、Magentic 等 orchestration。生态仍在迁移期，AutoGen/Semantic Kernel 用户需要重新对齐概念。.NET/Python 企业应用，多 agent workflow 与云集成。
7CrewAIRole/task/crew 抽象直观，Flows 负责状态和执行顺序，社区大。深度恢复、精细权限和复杂图状态需要额外工程。业务团队式 agent、内容/研究/运营自动化、快速落地。
8Google ADK代码优先、面向生产部署，支持多 agent hierarchy 和工具生态。跨语言和云平台路径需要按 Google 生态理解。Google/Gemini 生态里的可部署 agent 服务。
9OpenAI Agents SDKAgent = instructions + tools + handoffs，handoff/agents-as-tools/tracing/guardrails 清晰。持久队列、复杂 checkpoint 和跨进程恢复要自己补。轻量服务集成、specialist handoff、应用内 agent orchestration。
10AutoGen / AG2多 agent conversation 和 group chat 范式成熟，研究和 demo 资产多。共享对话容易上下文污染；微软官方路线已向 Agent Framework 收敛。协商、辩论、角色互动、实验性多 agent workflow。
11Strands Agents文档覆盖 agents-as-tools、swarm、graph、workflow 等模式，AWS 生产语境明确。社区规模小于 LangGraph/CrewAI。AWS 生态、模式学习、agent harness。
12MetaGPT / CAMELSOP、role society、multi-agent research 影响深。更像方法论和研究范式；治理、恢复、权限要另补。理解角色分工、SOP 分解、多 agent research。

为什么 Codex 排能力第一？不是因为它 stars 最高，而是因为它把 subagent 相关的工具规格、thread metadata、mailbox、wait、activity event、UI protocol 和 parent terminal notification 串成了一个闭环。这个闭环对“coding agent 如何安全并行工作”非常稀缺。

五、五种 team topology：不要用一种模式解释所有系统

5.1 Handoff / specialist routing

Handoff 模式下，主 agent 判断任务类型，然后把控制权或子任务交给 specialist。OpenAI Agents SDK 的 handoffs 文档把 handoff 表达成类似 transfer_to_* 的工具；multi-agent 文档则把 agent 定义为 instructions、tools 和 handoffs 的组合。Claude Code 的 subagent 也属于这个家族：定义专家，主 agent 选择并调用。

它适合边界清楚的任务：让 researcher 查资料，让 reviewer 看 diff，让 tester 设计测试。它不适合高度耦合的计划，因为 specialist 之间缺少共享状态和全局调度。

5.2 Supervisor / manager

Supervisor 模式让一个中心 agent 分派任务给 worker，再合成结果。LangGraph 的 supervisor把 specialized agents 暴露成 handoff tools；LangChain 的 multi-agent 文档也把 supervisor/router 作为核心模式。CrewAI 的 crew/manager、Microsoft Agent Framework 的 Magentic orchestration 都可以放在这一类。

它的优势是 ownership 明确：supervisor 负责拆解、监督、整合。它的风险是 supervisor 成为瓶颈，或者 worker 输出被直接拼接，没有足够核验。

5.3 Group chat / debate

Group chat 模式让多个 agent 共享对话频道，通过 manager 或规则控制发言。AutoGen 的 agent chat和新版 group chat design pattern是经典代表；AG2 的 group chat 文档延续了这条路线；Semantic Kernel 也提供 group chat orchestration。

它适合辩论、头脑风暴、共识形成，但最容易上下文污染。所有 agent 都看同一条 conversation 时，隔离边界变薄，token 成本也上升。生产系统里如果用 group chat，通常要配 manager、round limit、termination rule 和 transcript filtering。

5.4 Graph / workflow

Graph/workflow 模式把 agent 工作变成显式状态机或 DAG。LangGraph 是最典型的 graph runtime；CrewAI Flows 把状态和执行顺序从 Crew 里拆出来；Google ADK 的文档和 codelab 也强调 multi-agent system 的构建；Strands 的 multi-agent patterns覆盖 graph、workflow 和 swarm。

它适合业务流程、审批链、分支、重试和 checkpoint。缺点是开发者必须认真建模 state。如果你只想“让一个 reviewer 看一下”，graph 可能过重；但如果你要可恢复生产流，graph 是最稳的基础之一。

5.5 Durable task board

Durable board 是最像真实团队协作的一类：任务有状态、worker 有所有权、结果有结构、失败能重试。Hermes Kanban 是本文最完整的源码样本；OpenClaw 的 task runtime 也把 subagent/acp/cli/cron 放入统一任务类型。它适合小时级、天级或多人可见的 agent work。

它的代价是重。你需要 task schema、dispatcher、stale detection、ownership、artifact store 和 dashboard。但只要任务跨越一个模型回合，或者需要用户稍后检查，durable board 就比“开几个后台 agent，希望它们回来”可靠得多。

六、落地决策：什么时候用 subagent，什么时候别用

6.1 用工具，而不是 subagent

如果任务是确定性的、输入输出清楚、无需解释性探索，就应该写成 tool。读取文件、跑测试、格式化、查询数据库、调用 API，通常都不是 subagent 的职责。Subagent 不是为了替代函数，而是为了处理需要模型判断、搜索、比较、总结和验证的子问题。

6.2 用 subagent，而不是 team

如果任务能用一个短 brief 讲清楚，和主上下文耦合不强，成功标准明确，可以并行探索，就适合 subagent。这里的短 brief 通常是一个段落量级；图里的 200 words 只是经验上限，不是硬规则。典型例子是“请独立审查这个 diff 的安全风险”“请读某个模块并总结 API 边界”“请找出三种实现方案的 tradeoff”。这时不需要多 agent 群聊，只需要一个隔离专家返回 evidence。

6.3 用 team runtime，而不是一堆 subagent

如果多个角色之间有依赖关系，或者需要 supervisor 控制计划，就应该上 team runtime。比如 researcher 的结果决定 implementer 怎么改，tester 的结果可能要求 implementer 返工，reviewer 必须在 patch 后执行。这里需要状态、边、合并规则和失败路径，而不是随手 spawn 三个子 agent。

6.4 用 durable board，而不是一次性 team

如果任务跨越多个小时、需要等待外部资源、需要用户稍后回来、需要并发 worker、需要重试和审计，就应该进入 durable board 或 queue。Hermes Kanban、OpenClaw task runtime、LangGraph checkpoint 都属于这条线。一次性 team 很难处理进程重启、半完成 artifacts、用户中断和跨天恢复。

七、最常见的失败模式

7.1 盲目 fork 全上下文

Fork 全历史看起来省事，但会把 token 成本、隐私范围和指令污染一起复制给子 agent。更稳的默认是 isolated brief：给目标、约束、必要文件、成功标准和输出格式；只有子任务真的依赖当前细节时才 fork。OpenClaw 的 context modes 明确区分 isolated 和 fork，这个设计非常可迁移。

7.2 权限复制过宽

父级能写文件、联网、读环境变量，不代表子级也应该能做。Hermes 默认 blocked tools、OpenClaw subagent tool policy、Claude Code scoped tools、Codex fork/role 约束都在解决同一个问题：子 agent 的工作面应该比父级窄。尤其是 reviewer、researcher 这类角色，默认只读通常比默认可写更合理。

7.3 父级放弃验收

最危险的多 agent 失败不是子 agent 答错，而是父级把子 agent 的输出当成最终事实。好的系统会把 child result 变成 report/evidence，并要求 parent verify。OpenClaw completion metadata 里有 review instruction，Hermes completion handoff 要结构化 result，Codex child terminal turn 回到 parent mailbox，都是同一个原则。

7.4 用轮询代替等待协议

如果一个系统只能让父级不断问“你做完了吗”，它还不是成熟 runtime。Codex 有 wait_agent 和 collaboration waiting events；OpenClaw 建议 spawn 后 sessions_yield，completion push 回 requester；Hermes Kanban 用 watcher/dispatcher 循环。等待本身应该被建模，而不是藏在 prompt 里。

7.5 没有 trace 和 transcript

多 agent 的调试难度随 agent 数量增长。没有 transcript、task id、parent id、child id、event stream 和 artifact link，就很难回答“谁改了这个文件”“这个结论来自哪个子任务”“为什么任务重试”。Claude Code hooks、Codex protocol events、Hermes observability、OpenClaw task/session metadata 都说明：可观测性不是锦上添花，而是 subagent/team runtime 的基础设施。

八、结论：好的 subagent 系统把自由度变成边界

Subagent/team 技术的最终目标不是模拟一个热闹的办公室，而是把模型的自由度变成可控边界。Codex 给我们看到了 thread tree + mailbox + protocol event 的产品级闭环；Claude Code 给我们看到了 specialist subagent contract 如何成为用户可维护的角色库；OpenClaw 给我们看到了 subagent 如何进入 Gateway、session、channel、sandbox 和 ACP 的运行平面；Hermes 给我们看到了 delegation 和 durable Kanban 如何把长任务变成可审计的团队操作系统。

开源生态里，LangGraph、CrewAI、OpenAI Agents SDK、Google ADK、Microsoft Agent Framework、AutoGen/AG2、CAMEL、MetaGPT、Strands 各自解决不同层级的问题。最实用的选择方式不是追最新名词，而是从任务形状反推 runtime：能用 deterministic tool 就别上 agent；能用 isolated subagent 就别上 team；需要状态和恢复时用 graph 或 durable board；只要有权限风险，就先收紧工具和上下文。

如果只能留下一条规则，就是：子 agent 负责产生证据，父 agent 负责承担判断。这条 ownership 边界一旦丢掉，再多 agent 也只是把不确定性放大。
