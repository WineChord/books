上下文管理：从 Codex、Claude Code、OpenClaw、Hermes 到开源 Memory 生态

上下文管理不是“把更多 token 塞进窗口”，而是把每一种状态交给正确 owner，再在每一轮调用前投影成可预算、可审计、可恢复、可撤销的 model view。本文以 Codex、Claude Code、OpenClaw、Hermes Agent 的源码与文档为主线，结合 mem0、Graphiti、Letta、Supermemory、MemOS、LangMem、LlamaIndex、Cognee、Zep、AutoGen、Semantic Kernel、CrewAI 等实现，按热度和能力拆开排序。

开场：上下文不是文本长度

过去一年，很多讨论把 context management 简化成三件事：更长的 context window、更便宜的 prompt cache、更聪明的 memory。这个说法容易错，因为它把不同 owner 的状态混成了一个容器。一个 agent 真正面对的不是“上下文够不够长”，而是：

  1. 本轮模型到底能看见什么？
  2. 运行时还握有哪些模型看不见、但会影响行为的状态？
  3. 原始历史在哪里，压缩后的摘要是否能被重放和审计？
  4. 跨 session 的记忆是否有 scope、source、TTL、删除路径和权威等级？
  5. provider cache 的前缀复用是否被动态内容破坏？

我用一个公式定义本文的讨论对象：

\( V_t = \Pi(B_t, E_t, H_t, C_t, M_t, R_t) \)

其中 \(V_t\) 是第 \(t\) 轮模型可见视图；\(B_t\) 是 provider boundary 和 cache 状态；\(E_t\) 是 runtime envelope，例如工具、权限、当前目录、日期和审批策略；\(H_t\) 是原始 transcript；\(C_t\) 是 compaction、summary、checkpoint；\(M_t\) 是长期 memory；\(R_t\) 是外部检索结果。上下文管理就是投影函数 \(\Pi\)：它决定哪些状态在这一轮出现、以什么位置出现、带什么权威标签出现、占用多少 token。

这个定义的好处是能解释很多看似矛盾的工程选择。OpenAI 和 Anthropic 的 prompt caching 都强调稳定前缀；Codex 的 TurnContext 把本轮运行时状态明确装进一个 envelope；Claude Code 通过 CLAUDE.md 和 auto memory 把跨 session 指令显式化；OpenClaw 让 context engine 插件负责组装、压缩和召回；Hermes Agent 把 context compressor、provider cache、external memory 和 scrubber 拆成不同边界。它们不是同一个功能的不同名字，而是不同 owner 的状态治理。

证据边界：本文的源码级判断使用公开仓库和不可变 commit 链接；Claude Code 的源码细节来自可公开访问的镜像快照，并辅以官方 memory 文档。GitHub star 是 2026-06-16 调研时的公开页面近似快照，只用于衡量 adoption proxy，不作为质量、稳定性或安全性的证明。

一、六个 owner：先分权，再谈上下文

上下文管理的第一步不是选向量库，也不是写摘要 prompt，而是把状态 owner 分清楚。一个成熟 agent 至少有六层状态：provider cache、model view、runtime envelope、transcript ledger、compaction/checkpoint、memory/retrieval。

1.1 Provider cache：缓存不是记忆

OpenAI 的 prompt caching 文档把缓存描述成自动发生在长 prompt 上的前缀复用；实践建议是把静态内容放在 prompt 开头，把每轮变化的用户输入放在结尾。Anthropic 的 prompt caching 文档则更显式地暴露 usage counters，例如 cache_creation_input_tokens 和 cache_read_input_tokens，并说明工具、system、messages 等块的缓存失效层级。二者共同说明一件事：provider cache 优化的是重复前缀的 latency 和 cost，不负责事实是否仍然正确，也不负责跨 session 的语义治理。

\( \mathrm{input}=\mathrm{cache\_read}+\mathrm{cache\_creation}+\mathrm{uncached} \)

缓存优化最怕动态内容污染前缀。工具 schema、长系统说明、稳定项目规则、固定检索材料适合靠前；当前用户输入、时间、随机 session id、临时工具结果适合靠后。cache hit 下降不是 memory 系统坏了，而是 provider owner 的边界被破坏。

1.2 Model view：所有长期状态最终都要投影

模型只看见本轮被投影进去的 view。长期 memory、checkpoint、workspace 文件、检索结果、运行时指令都不是天然可见的；它们必须被 runtime 选择、排序、裁剪、标权威、注入。Codex 的 ContextManager 明确维护 transcript、history_version、token_info 和 reference context item，并在 for_prompt 投影时过滤和规范化历史项（见 history state 与 prompt projection）。这就是上下文管理的中心：ledger 和 view 要分离。

如果一个系统把“原始历史”和“本轮 prompt”当成同一个数组，它迟早会遇到两类错误：一是为了省 token 删除了恢复所需的原始事件；二是为了保留恢复能力，把模型不该看到的内部状态也塞进 view。

1.3 Transcript、compaction 与 checkpoint：压缩不是删除

Transcript 是事实账本；compaction 是 view 的重写；checkpoint 是恢复点。三者经常被混用。Codex 的 compact 逻辑会克隆历史、加入本轮压缩请求、在溢出时裁掉最旧消息，同时尽量保留 prompt cache 前缀和最近消息（见 compact flow），最后构造“摘要 + 近期消息”的 compacted history（见 compacted history builder）。OpenClaw 的 compaction 文档也把 full history on disk、recent messages intact、summary in transcript 区分开来，并明确 compaction 不等于 pruning（见 compaction overview 与 compaction vs pruning）。

LangGraph 把 checkpoint 抽成另一类 owner：checkpointer 按 thread 持久化 graph superstep，让 human-in-the-loop、失败恢复和 memory 成为状态机的一部分。它解决的不是“摘要怎么写”，而是“任务中断后从哪里继续，pending writes 是否会重复执行”。

二、四条运行时主线

上下文管理的实际形态由宿主 runtime 决定。memory provider 可以很强，但如果 runtime 不知道什么时候读、什么时候写、如何降级、如何标权威、如何避免泄漏，它只能变成另一个 prompt 拼接器。

2.1 Codex：TurnContext + ContextManager + compact

Codex 的源码非常适合做 baseline。TurnContext 是本轮上下文 envelope：它包含 model、provider、reasoning、session source、environment、cwd、日期、时区、developer/user instructions、collaboration mode、approval policy、permission policy、network、features、truncation、dynamic tools、turn skills 等字段（见 TurnContext fields）。这不是给模型看的聊天历史，而是 runtime 用来决定本轮行为的控制面。

codex-rs/core/src/context/mod.rs 又把 environment、permissions、realtime、skills、plugins、hooks、token budget、user instructions 等 context fragments 模块化导出（见 context fragments）。这意味着 Codex 的“上下文”不是一个字符串，而是一组可单独生成、排序、预算和替换的结构。

压缩上，Codex 还定义了 COMPACT_USER_MESSAGE_MAX_TOKENS 与 initial context reinjection 的语义：手动压缩、pre-turn 压缩、mid-turn 压缩的上下文注入位置不同（见 compact constants and injection modes）。这是一条重要经验：压缩不是“老消息变短”，而是改变模型看到的时间结构。如果 mid-turn 注入位置不对，模型会把旧上下文误读成最新用户意图。

2.2 Claude Code：文件型记忆与 compact boundary

Claude Code 的官方 memory 文档把 CLAUDE.md 和自动 memory 作为会话之间的持久知识：每个 session 仍然有新的 context window，但项目约定、偏好和经验可以通过这些文件和自动记忆重新载入。这个路径的优势是可审阅、可提交、可让团队协作；风险是文件里既可能有项目事实，也可能有操作流程、偏好、临时计划，权威等级要靠写法和 runtime 约束维持。

公开镜像源码展示了更具体的 runtime 侧做法：getSystemContext 与 getUserContext 组合 git status、工作目录、日期、项目 memory 和 user memory，并用 cache breaker 控制上下文缓存（见 context assembly）。消息侧则有 compact boundary、microcompact boundary、snip projection 和“compact boundary 之后消息”的投影函数（见 compact boundary helpers）。buildPostCompactMessages 会按 boundary、summary、保留消息、attachments、hook results 的顺序重建压缩后消息（见 post-compact assembly）。

Claude Code 这条线提醒我们：文件型 memory 的可维护性很强，但必须配套边界消息和投影规则。否则 CLAUDE.md、summary、hook result、tool result 会在 model view 里混成同等权威，读者和模型都不知道谁该覆盖谁。

2.3 OpenClaw：context engine 插件与投影安全

OpenClaw 把 context engine 明确写成可替换能力。它的 context engine 文档描述了 ingest、assemble、compact、after turn lifecycle；在 Codex harness 下，组装出的上下文会被投影进 Codex developer instructions 和当前 prompt，同时 Codex 仍然拥有 native history 与 compactor（见 context engine lifecycle）。接口上，ContextEngine 提供 AssembleResult、messages、estimatedTokens、systemPromptAddition、promptAuthority 等字段（见 context engine interface）。

这层设计非常关键：OpenClaw 不是把所有 memory 直接塞给模型，而是通过 projection layer 包装成 quoted reference，提示模型这些材料是 untrusted/reference context，并生成 developer instruction addition（见 context projection）。active memory 文档进一步把 plugin-owned memory subagent 放到主回答之前，并说明它的内部 prompt prefix 不应作为普通用户可见文本泄漏（见 active memory boundary）。

OpenClaw 的强项不是“替代 Codex 压缩”，而是在本地、多插件、多助手入口的环境里，把上下文装配权从核心 runtime 中抽出来，同时保留权威标签和安全投影。

2.4 Hermes Agent：压缩、缓存、memory provider 与 scrubber

Hermes Agent 的上下文设计有两个层次。第一是 context engine plugin：文档说明插件可以替换内置 ContextCompressor，一次只启用一个，且不会自动激活；接口包含 update_from_response、should_compress、compress 等方法（见 plugin overview 与 plugin ABC）。第二是 compression and caching：文档把 gateway session hygiene 触发点、agent compressor 触发点、Anthropic prompt caching 结合起来，并给出四阶段压缩算法：剪裁旧工具结果、确定边界、结构化摘要、组装压缩后消息，以及必要时迭代重压缩（见 compression thresholds 与 compression algorithm）。

源码里，Hermes 的 summary prefix 明确把压缩摘要标为 reference only，并强调最新用户消息和 memory 拥有更高权威（见 summary prefix）。它还在 session reset / session end 清理 previous summary，避免跨 session 泄漏（见 summary reset），并用“最近两次压缩节省低于阈值则跳过”的 anti-thrashing 规则防止无意义压缩循环（见 anti-thrashing guard）。

memory 侧，MemoryManager 只有一个外部 provider，负责 pre-turn prefetch、post-turn sync 和 queued prefetch；它还清理 memory context tags，并有 streaming scrubber 防止分块输出时泄漏内部标记（见 memory manager overview 与 sanitize and scrubber）。这是一条生产经验：memory provider 可以失败、延迟或离线，但内部 memory prompt 不能泄漏给用户。

三、生态排序：热度榜和能力榜要分开

上下文管理生态很容易被“谁 star 多”误导。OpenClaw、Hermes、Claude Code、Codex 是 agent runtime；mem0、Supermemory、Zep、Cognee 更像 memory/context platform；Graphiti 是 temporal graph engine；LangGraph 和 AutoGen 是 agent framework；LlamaIndex 和 Semantic Kernel 有很强的 retrieval/vector/store 抽象；CrewAI 更偏 crew/workflow 产品体验。它们不应该放进一个“最好用”表里直接比较。

3.2 能力榜：按场景分组排序

能力榜不能只有一条线。运行时上下文控制、产品级长期记忆、时间关系图谱、stateful agent 平台、framework-native context 是五类不同问题。下面的排序只在同一场景内比较：未进入某组不等于能力弱，通常只是它的主问题不在这一层。

场景 组内排序 为什么这样排 不该误读
运行时上下文控制 Codex → OpenClaw → Hermes Agent → Claude Code Codex 最适合作为源码级参考：TurnContext、history ledger、prompt projection、token pressure 与 compaction 边界最清楚；OpenClaw 把 context engine 插件化；Hermes 把 compressor、cache、external memory 和 scrubber 拆清；Claude Code 强在文件型 memory 与 compact boundary。 这组不是 memory API 排名。它回答的是“每轮调用前 model view 怎样被组装、压缩和审计”。

四、实现模式：Memory、RAG、Wiki、Graph、Checkpoint 都在管上下文

业界实践不是一条线，而是一组互补模式。向量 memory 负责语义相似；graph memory 负责关系与时间；artifact wiki 负责可审阅 synthesis；checkpoint 负责任务恢复；RAG 负责外部资料；runtime compaction 负责窗口压力。把它们混成一个“上下文库”会让选型失真。

4.1 向量与混合检索：mem0、LlamaIndex、Semantic Kernel

mem0 的配置对象包含 vector store、LLM、embedder、history DB、reranker、custom instructions 等字段（见 MemoryConfig）。Memory.add 会解析消息、检索已有 memory、调用 LLM 抽取，再写入 vector store；search 支持 user/agent/run 过滤、advanced filters、vector search 和可选 rerank（见 add pipeline 与 search pipeline）。这类实现的关键不是“用了向量库”，而是 scope filter 和 rerank 能不能挡住跨用户、跨 agent、跨 run 污染。

LlamaIndex 的 memory 模块把短期 FIFO、token_limit、chat_history_token_ratio、token_flush_size 与长期 memory blocks 区分开来：短期消息超限后会 flush，长期 block 可以作为 system 或 latest user content 注入（见 memory model 与 flush path）。Semantic Kernel 则长期提供 agent、plugin、memory 与 planning 组合，并在数据层提供 VectorStore 抽象（见 agent framework overview 与 memory glossary），更适合已经在 SK ecosystem 内构建 agent、plugin 和 process orchestration 的团队。

4.2 时间图谱：Graphiti、Zep、Cognee

Graphiti 的 README 把自己定义为 temporal context graph：实体、事实、episode 都能随时间演化，并通过 semantic、keyword、graph traversal 的 hybrid retrieval 召回。源码中 add_episode 会抽取节点和边、解析并更新图；search recipes 则组合 hybrid search、BFS 和 cross encoder（见 Graphiti overview 与 hybrid search recipe）。

Zep 是 Graphiti 背后的托管 context platform：README 把流程概括为 add context、Graph RAG、retrieve & assemble，并强调 relationship-aware context blocks（见 Zep overview 与 context assembly）。Cognee 则走 self-hosted knowledge graph 路线：README 描述它把任意格式数据 ingest 成长期 memory，并结合 vector embeddings、graph reasoning 和 ontology generation；其 Claude Code plugin lifecycle 会在 SessionStart、PostToolUse、UserPromptSubmit、PreCompact、SessionEnd 等 hook 上捕获和注入 memory（见 Cognee overview 与 Claude Code lifecycle）。

图谱 memory 的优势是解释“事实什么时候变了、谁和谁有关、这个关系从哪个 episode 来”；成本是 schema、索引、冲突和查询调参都会比普通 vector memory 重。

4.3 状态块与 agent OS：Letta、MemOS、Supermemory

Letta 的 memory schema 直接把 context window 拆成 archival、recall、core、summary、tool/function、messages 等 token 计数，并把 core memory blocks 渲染成 model-readable memory block（见 context window overview 与 memory block rendering）。这是 stateful agent 的代表：memory 不只是外部检索，而是 agent identity 和 working state 的一部分。

MemOS 的 OpenClaw app README 把目标写成 persistent local conversation memory，并列出 auto-capture、dedup、chunking、hybrid retrieval、MMR、recency decay、skill evolution、team sharing 等能力。源码里 recall engine 会组合 FTS 与 vector candidates，再用 RRF、MMR、recency decay 排序；capture 侧会跳过 system/self tools、剥离 metadata/thinking/evidence；ingest worker 则做 exact hash dedup 和 smart dedup（见 hybrid recall、capture filters 与 ingest dedup）。

Supermemory 的文档把 documents 和 memories 分开：documents 是 raw inputs，memories 是语义 chunk、关系和会演化的事实；graph memory 关系包括 update、extend、derive，并讨论 automatic forgetting、contradiction resolution 和 noise filtering（见 memory engine、dynamic memories 与 contradiction handling）。这条线适合把 memory 当产品级 context layer，而不是低层库。

4.4 Multi-agent context：AutoGen、CrewAI、LangGraph

AutoGen 的 ChatCompletionContext 抽象提供 unbounded、buffered、token-limited 等 model context，agent 和 group chat 可以持有各自的 model context（见 base context 与 token-limited context）。这类抽象的核心问题是“多 agent 谁看见哪段历史”。

CrewAI 的 docs 暴露了 memory、respect_context_window、knowledge_sources 等配置，并把 flow memory 和 human feedback 纳入后续执行的 context（见 flow memory 与 human feedback context）。它适合 workflow 产品，但团队要特别注意 telemetry 和共享配置：一旦把 task context、goal、backstory、output 作为可观察数据，就要把隐私和审计写进运行策略（见 telemetry boundary）。

LangGraph 则不是 memory provider，而是状态机骨架。checkpointer 让每个 thread 的 graph state 可恢复，store 让跨 thread memory 可持久化；LangMem 在此基础上提供 manage/search memory tools 和 background memory manager（见 LangGraph checkpointer、LangGraph store 与 LangMem overview）。对已经用 LangGraph 的系统来说，这是最自然的集成路径。

五、失败模式：状态进错 owner

上下文管理事故通常不是模型“不够聪明”，而是状态被放错层。一个旧摘要被写成命令，一个工具结果被裁掉，一个动态时间戳插进缓存前缀，一个 memory provider prompt 泄漏给用户，都会让系统表现得像随机失控。

5.1 陈旧摘要变指令

压缩摘要最危险的错误是 imperative drift：摘要为了节省 token，把旧用户意图写成“你现在必须……”，下一轮模型又把它当成当前指令。Hermes 的 summary prefix 把摘要标成 reference only，并强调 latest user wins；这是正确方向。Codex 和 Claude Code 的 compact boundary 也都在解决同一个问题：压缩后的历史必须保留时间与权威结构。

5.2 孤儿工具结果与工具调用配对

工具调用和工具结果是一对。裁剪历史时如果留下 tool call、删掉 tool result，模型可能尝试重放、误读或生成无效后续。OpenClaw 的 compaction 文档强调 identifier preservation 和 active transcript byte guard；Hermes 的压缩算法先处理旧工具结果，再确定 boundaries。这个问题在 coding agent 特别严重，因为一次工具调用可能代表文件变更、shell 结果或权限决策。

5.3 Memory 作用域串线

用户偏好、项目规则、团队流程、客户事实不能共享同一个 namespace。mem0 的 search 要求 user_id、agent_id、run_id 这类过滤条件；LangMem 通过 namespace scoping 控制 store；MemOS 区分 local 与 hub memories。这些都是在防止“个人喜欢用 pnpm”被写成“整个组织必须用 pnpm”。

5.4 内部上下文泄漏

memory context、provider prompt、context engine trace 都可能因为 streaming chunk 边界泄漏到用户输出。Hermes 的 streaming scrubber、OpenClaw 的 active memory 隐藏 prefix、Codex 的 prompt projection 都在处理这个问题。生产系统要做两层扫描：模型输出前的 streaming scrub，和页面发布前的静态泄漏检查。

六、选型路线：先问状态归属

选型时不要先问“用 mem0 还是 Graphiti”，而要先问新信息要活多久、对谁生效、需要什么证据、是否必须删除、是不是关系随时间变化。

七、可迁移规则

把所有实现放在同一张地图上后，可以提炼出十条规则：

  1. ledger 和 view 必须分离。 原始 transcript 用于恢复和审计；model view 是每轮投影结果。
  2. 压缩摘要只能是 reference，不应变成最新指令。 最新用户意图和明确 memory/policy 拥有更高权威。
  3. read path 和 write path 要拆开。 当前模型不应直接把自己本轮输出写成下一轮长期指令。
  4. provider cache 只管前缀复用。 它不是 memory，也不负责事实新鲜度。
  5. scope 是 memory 的第一字段。 user、project、team、org、agent、run 混用会造成长期污染。
  6. 工具调用和工具结果要成对保留或成对摘要。 不要留下孤儿 call/result。
  7. 检索命中不是注入许可。 候选还要经过 rank、dedupe、budget、authority label、redaction。
  8. 图谱 memory 解决关系和时间，不是 vector store 的高级包装。 只有需要 temporal validity 和 provenance 时才值得承担成本。
  9. 内部 context block 要有泄漏防线。 streaming scrubber 和静态扫描都要做。
  10. 排序要分热度和能力。 star 数解释 adoption risk，能力解释上线风险，场景决定最终选择。

上下文管理的最终目标不是让 agent “记得更多”，而是让它在每一轮都知道：什么是当前任务，什么是历史证据，什么是长期偏好，什么是外部资料，什么是可执行指令，什么只是参考。只要这个边界清楚，长窗口、cache、memory、RAG、graph、wiki、checkpoint 才会从互相抢 token 的材料，变成可以组合的状态工程。
