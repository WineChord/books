Agent Evals 与 Observability：从源码到开源生态的工程地图

阅读契约：这篇文章回答一个问题：一个能写代码、调用工具、维护长期上下文的 agent，应该怎样同时被评测和被观测？

读的时候请跟踪三类 owner：离线 eval owner、runtime observability owner、生产反馈 owner。读完之后，你应该能判断一个开源工具到底是在做数据集评测、trace 采集、LLM-as-judge、红队、实验管理、生产监控，还是把它们连成了闭环。

很多团队第一次给 agent 做质量体系时，会先写一组 prompt 测试：输入问题，跑模型，拿输出和期望答案比一比。这个阶段很自然，因为它像普通单元测试。但真正上线以后，问题很快变形：模型没有直接答错，却选错工具；答案正确，但用了 6 倍 token；本地 eval 通过，生产里某个仓库规则让上下文溢出；一次失败看起来是模型幻觉，回放 trace 后才发现是工具返回被截断。

这就是 evals 和 observability 必须放在一起讲的原因。evals 负责在可控数据集上回答“这个系统在已知任务上是否变好”；observability 负责在真实运行中回答“它为什么这样做、代价是多少、失败边界在哪里”。对 agent 来说，二者不是前后两个团队的事情，而是一条证据链的两种投影。

本文以四个 agent runtime 为主线：Codex、Claude Code 公开源码镜像、OpenClaw、Hermes Agent。再把它们和 Langfuse、Phoenix、promptfoo、DeepEval、OpenAI Evals、Opik、TensorZero、Portkey gateway、Helicone、OpenLLMetry、OpenInference 等开源实现放到同一个地图里看。

证据边界也先说清楚。官方产品能力、协议和 API 语义以官方文档和公开仓库为准；源码机制只在链接到的公开 commit、文件和行号范围内成立；Claude Code 这里使用的是公开源码镜像，不等同于 Anthropic 官方源码发布，也不用于推断 Anthropic 服务端内部实现。排名数据来自 2026-06-16 的 GitHub API 查询，stars 只是流行度信号，不等于技术适配度。

一、先把 eval 和 observability 分开，再合起来

1.1 Eval 回答“是否满足任务契约”

一个 eval 最小需要四个东西：数据集、运行器、评分器、决策规则。数据集定义输入和期望行为；运行器把同一批任务送进同一个系统；评分器把输出压成可比较的事实；决策规则决定是否允许合并、发布、回滚或继续观察。

{
  "case": {
    "input": "修复这个失败测试并说明原因",
    "workspace": "fixture: repo-with-bug",
    "expected": {
      "tests": "pass",
      "diff_policy": "minimal",
      "explanation": "names the root cause"
    }
  },
  "run": {
    "agent": "candidate-runtime",
    "model": "selected-model",
    "tools": ["read", "edit", "shell"]
  },
  "scores": {
    "task_success": 1,
    "patch_quality": 0.82,
    "tool_budget": 0.74
  },
  "gate": "block if task_success < 1 or patch_quality < 0.75"
}

这里的重点不是“评分器是不是一个 LLM”。评分器可以是断言、正则、单元测试、检索指标、pairwise judge、人审 rubric，或者它们的组合。真正重要的是它能否稳定地把任务契约转成决策信号。

1.2 Observability 回答“运行中发生了什么”

Observability 的最小单位不是 test case，而是一次运行的事实链：trace、span、log、metric、event、artifact。对普通后端服务来说，trace 解释请求为什么慢；对 agent runtime 来说，trace 还要解释模型看到了什么、调用了什么工具、工具返回了什么、哪一步触发恢复、token 和成本在哪里增长。

这就是为什么 OpenTelemetry 体系在 agent 领域变得重要。它不是因为所有问题都要上云端可观测性平台，而是因为 agent 的失败经常跨越模型、工具、文件系统、网络、UI 和持久化记录。没有 trace context，失败会碎成几段日志；没有低基数字段，观测后端会被 prompt 和路径打爆；没有内容采集开关，调试会直接变成数据泄露风险。

1.3 为什么 agent 不能只做一种

只做 eval，会得到一组漂亮的离线分数，却不知道真实失败时系统看见了什么。只做 observability，会有很多漂亮的 trace，却没有稳定门禁告诉你一次改动是否让关键任务退化。agent 的质量闭环要同时持有两种事实：

问题 Eval 更擅长 Observability 更擅长 闭环做法
新模型是否可替换旧模型 固定数据集、固定 budget、固定 scorer 对比 上线后成本、延迟、工具错误和回退路径 先用 regression suite gate，再用 production drift 监控
工具调用为什么失败 可复现 fixture 和 expected tool sequence 真实 span、stderr、重试、超时、权限和 traceparent 把失败 trace 提炼成 eval case，而不是只修 prompt
RAG 或代码检索是否退化 context precision、faithfulness、answer correctness 检索 span、召回条目、context token、cache 命中和索引版本 指标判断结果，trace 解释原因
是否存在安全或数据泄露风险 红队插件、policy judge、越权任务集 内容采集 gate、PII redaction、低基数字段和审计日志 风险 eval 进 CI，高风险 trace 进审计队列

二、从四个 agent runtime 看观测面的真正 owner

2.1 Codex：先记录 rollout，再把事实投影成 telemetry

Codex 的一个关键特点是把会话历史、回滚、分叉和恢复放在 rollout 事实链里，而不是只看最终 prompt。可见源码里，`user_message_positions_in_rollout` 会扫描 rollout items 找用户消息边界，并且在遇到 ThreadRolledBack 事件时修正有效历史；`fork_turn_positions_in_rollout` 则把真实用户消息和触发 turn 的 inter-agent communication 都视为 fork 边界。

这说明 Codex 的可观测性并不只是“把 API 延迟打点”。它先保留足够的运行事实，让后面的 resume、rollback、fork、replay 可以解释“当前有效历史是怎么来的”。如果只记录最终模型请求，回滚后的线程会像被神秘截断；如果只记录 UI，fork 的触发边界会被普通聊天消息淹没。

在跨系统 trace 上，Codex 还有单独的 W3C trace context 处理。`current_span_w3c_trace_context` 从当前 tracing span 注入 traceparent / tracestate；`context_from_trace_headers` 则从 headers 反向恢复上下文。这个边界的价值在于：本地 runtime、远端任务、provider 请求和下游日志可以共享一个可传播的 trace 语义，而不是各自发明 request id。

Codex 也把低层组件的 telemetry 做成可插拔 sink。`DbTelemetry` 明确要求数据库行为不依赖 telemetry 是否发送成功；`SseTelemetry` 和 `WebsocketTelemetry` 把 transport 层的 poll、request、event 单独抽象出来。这里的设计纪律很清楚：先让业务路径可恢复，再让每个边界可测量，而且 telemetry 失败不能反过来改变业务结果。

2.2 Claude Code：analytics 必须先过隐私与采样边界

Claude Code 的公开源码镜像显示出另一种压力：客户端 analytics 需要大量环境和工具上下文，但这些上下文也最容易泄露路径、代码片段、MCP server 名、skill 名或用户配置。它的 `isAnalyticsDisabled` 会受测试环境、第三方 provider、privacy level 等条件影响；`shouldSampleEvent` 对事件级采样做动态配置；`initialize1PEventLogging` 使用 OpenTelemetry logs SDK 建一个本地 provider，再通过批处理 exporter 发送内部事件。

更值得注意的是 metadata 层。`AnalyticsMetadata_I_VERIFIED_THIS_IS_NOT_CODE_OR_FILEPATHS` 这个类型标记不是运行时加密，而是让开发者在类型层明确承诺“这个字符串不是代码或文件路径”；`sanitizeToolNameForAnalytics` 会把 MCP 工具名收敛成 mcp_tool；tool input truncation 常量 则限制字符串、JSON 字符数、collection 个数和深度。

这类代码给 eval/observability 一个很实际的提醒：质量证据不应该通过“多发一点原始内容”来获得。agent 的输入常常就是代码、路径、token、客户数据和内部 prompt。没有采样、redaction、opt-out、低基数和内容开关，observability 很容易把调试系统变成另一个风险面。

2.3 OpenClaw：把 diagnostics 设计成 OTLP 产品面

OpenClaw 的观测面更像一个面向生产部署的 contract。它的 OpenTelemetry 文档直接把三层关系写清楚：in-process diagnostics events、diagnostics-otel plugin、OTLP/HTTP 导出的 metrics/traces/logs；同时说明 provider calls 会收到由 OpenClaw 信任的 model-call span context 生成的 W3C traceparent header，而 plugin 发出的 trace context 不会被传播。这个契约在 OpenClaw OpenTelemetry 文档的系统说明里是公开可读的。

它更重要的一点是内容采集默认关闭。文档的 privacy and content capture 部分明确说明，raw model/tool content 默认不导出，span 只携带 bounded identifiers；只有配置 diagnostics.otel.captureContent.* 时，才会把输入、输出、工具参数、工具结果、system prompt 或 tool definitions 作为受控内容导出。它还说明已有 caller-supplied traceparent 会被替换，避免 plugin 或自定义 provider options 伪造跨服务 trace 祖先。

OpenClaw 还把这些 contract 变成 QA 场景。`otel-trace-smoke` 的目标不是“能不能启动一个 agent”，而是验证 QA-lab gateway run 会通过 diagnostics-otel plugin 产生 bounded OpenTelemetry traces、metrics 和 logs，并且不泄露内容或原始诊断标识。这就是 eval 和 observability 交叉处最有价值的样子：eval case 检查观测 contract 本身。

2.4 Hermes Agent：把 eval harness 当成可测路径，而不是演示脚本

Hermes Agent 的观测面更偏工程实验。`tool_search_livetest.py` 用一组 fake MCP tools 构造真实形状的检索场景，记录 transcript、tool calls、实际调用、最终响应、timing 和 round-trip count；`benchmark_browser_eval.py` 对比 supervisor WebSocket 路径和 subprocess eval 路径的浏览器 runtime evaluate 延迟；`memory_monitor.py` 则把长进程 RSS、GC stats、thread count 做成 grep-friendly 的周期日志。

这类实现不一定像 Langfuse 或 Phoenix 那样提供完整产品 UI，但它非常适合 agent runtime 的内部质量工程：当你在改工具检索、浏览器控制、TUI 性能、内存泄漏时，最需要的不是一个通用平台，而是可复现、可比较、可贴进 PR 描述的实验记录。

三、Eval 的类型谱系：不要把所有分数都叫 benchmark

3.1 从最快到最真实，是一条连续谱

agent eval 的第一层误区，是把“有一批问题和一个平均分”都叫 benchmark。对工程系统来说，benchmark 只是 eval 的一种形态。更实用的谱系是从快到真：

类型 回答的问题 优点 盲点 代表实现
Unit checks 输出是否满足显式断言 快、便宜、适合 CI 难覆盖开放式推理 simple-evals、自定义断言
Prompt matrix 多个 prompt、provider、变量组合谁更好 适合回归测试和模型替换 容易停留在单轮输出 promptfoo、Prompt Flow
RAG metrics 答案是否忠实、检索是否相关 把回答和 context 分开测 指标依赖任务定义和 judge 稳定性 Ragas、DeepEval
Agent trajectory 路径、工具、恢复和最终状态是否正确 最贴近 coding agent 和 workflow agent 采集和回放成本高 Inspect、OpenAI Evals、内部 trace replay
Red team 是否会越权、泄露、被注入或违反 policy 能发现普通任务集发现不了的风险 分数不等于真实风险概率 promptfoo redteam、DeepEval safety metrics
Human review 系统在真实语境下是否可信 能覆盖审美、业务语义和边界判断 慢、贵、需要 rubric 和抽样纪律 Langfuse/Opik/Phoenix annotation queues、review workflows

3.2 Scorer 不是越智能越好

LLM-as-judge 很有用，但它不是默认答案。一个好的 scorer 应该先问：这个任务有没有可执行事实？如果 patch 可以跑测试，就先跑测试；如果工具必须按顺序调用，就检查 trace；如果答案必须引用来源，就检查 source attribution；只有当语义本身无法用 deterministic check 表达时，才把 judge 放进链路。

AutoEvals 的 `LLMClassifier` 是一个很典型的可复用 judge 形态：用 prompt 和 choice_scores 把开放式判断转成可比较分数；它还在 trace 参数上支持从多轮 thread 中取变量。这类 scorer 的价值在于快速搭建语义评估，但它必须和 deterministic scorer、人工抽查、分数校准一起使用。

3.3 Agent trajectory eval 要看路径，而不是只看最终回答

coding agent 的任务成功往往取决于路径：有没有读对文件、有没有误删、有没有跑测试、有没有处理失败命令、有没有把大型工具输出合理摘要。最终一句“已修复”可能完全正确，也可能只是自信地覆盖了失败。trajectory eval 要把 trace 当成一等输入。

{
  "trajectory": [
    { "span": "read_file", "target": "failing_test", "ok": true },
    { "span": "edit_patch", "changed_files": 1, "ok": true },
    { "span": "shell", "command": "npm test", "exit": 1 },
    { "span": "shell", "command": "npm test -- --runInBand", "exit": 0 }
  ],
  "scorers": [
    "final_tests_pass",
    "minimal_diff",
    "explains_failed_retry",
    "no_unapproved_network"
  ]
}

这个例子解释了为什么 observability 会反哺 eval：没有 trace，eval 只能看最后输出；有 trace，eval 才能判断“失败后是否恢复”“是否用了危险路径”“是否因为工具输出丢失而误判”。

6 Portkey gateway 网关能力强，README 明确定位为面向大量模型的 fast, reliable and secure routing，并在 功能清单里列出 retries、fallbacks、guardrails、agentic workflow 和 MCP gateway observability。 先统一 provider access、路由、guardrails、MCP gateway，再逐步接入 eval/trace 平台。
7 Helicone gateway/proxy 接入路径短，成本、日志、实验、监控上手快。 先从 provider call observability 和成本控制切入的团队。
8 Weave / TruLens / OpenLIT 各有优势：Weave 贴近 W&B 实验链路，TruLens 强调 feedback functions 和 records，OpenLIT 强调 OTel-native + guardrails + evals。 已经有对应生态或想采用轻平台的人。

4.4 Trace SDK / Semantic convention 赛道

这个赛道不是要替代平台，而是让你把 LLM/agent 调用转成标准 trace。OpenLLMetry 更像 provider/framework instrumentation 套件；OpenInference 更像 AI observability 的语义约定和 instrumentation 家族；AgentOps 则把 agent monitoring SDK、trace lifecycle 和 validation API 包在一起。AgentOps 的 `start_trace` / `end_trace` 就是典型 SDK-level trace lifecycle。

选择这类项目时，最重要的问题不是“有没有 UI”，而是它是否能进入你已有的 OpenTelemetry collector、Datadog、Grafana Tempo、Honeycomb、New Relic 或内部 trace backend。如果不能和现有观测面汇合，它很容易变成另一个孤岛。

五、Trace-to-Eval 数据模型：把生产事实变成可复现样本

5.1 关键对象不是 trace，而是 trace、dataset、score 的连接

最成熟的 agent 质量系统会把生产 trace 转成 eval case。这个转换不能直接复制原始 payload，因为 trace 里可能有 secret、路径、用户数据、版权内容、内部配置和一次性 token。正确的数据模型通常是：

{
  "trace": {
    "trace_id": "stable public id",
    "spans": ["model_call", "tool_call", "retrieval", "shell"],
    "metrics": ["latency", "input_tokens", "output_tokens", "cost"]
  },
  "normalization": {
    "redacted": true,
    "content_policy": "bounded fields only",
    "artifacts": ["fixture diff", "tool summary", "expected state"]
  },
  "dataset_item": {
    "input": "minimal reproducible task",
    "expected_output": "behavioral contract",
    "metadata": {
      "source": "golden trace",
      "failure_mode": "tool timeout then recovery"
    }
  },
  "scores": [
    { "name": "task_success", "score": 1 },
    { "name": "cost_budget", "score": 0.68 },
    { "name": "safe_tool_use", "score": 1 }
  ]
}

Langfuse 的对象模型很好地体现了这条链。它把 traces、observations、scores、dataset_items、dataset_run_items 都放在核心表名里；ingestion 服务会把 trace、observation、score 和 dataset run item 分开处理。这说明平台型 observability 的目标不是只画 trace 树，而是把 trace、dataset、score、prompt 和 experiment 变成可查询、可回放、可比较的对象。

5.2 promptfoo 的 OTLP receiver 说明 eval 工具也在吸收 trace

promptfoo 是 eval/CI 工具，但它也在吸收 observability 语义。它的 OTLP receiver 测试覆盖 JSON traces；同一测试文件还覆盖 ingest-time redaction 等行为。测试中还出现了把 Claude Code log 转成 claude_code.tool.execution child span 的断言，以及把 Codex log 通过 resource trace context 挂回 trace 的路径。

这很能说明趋势：eval runner 不再只读 prompt 和 output。它要知道一次 agent run 的 trace，才能把工具错误、日志、span linkage、redaction policy 和最终分数放在一起解释。

5.3 Phoenix 和 OpenInference 代表 trace schema 路线

Phoenix 的 `TracerProvider` 扩展 OpenTelemetry SDK，并用 Phoenix-aware defaults 配置 endpoint、project name、batch/simple processor。这个路线的价值是复用 OTel 生态：instrumentation 负责把 provider/framework 事件变成 spans，平台负责展示、筛选、标注、关联 eval。

OpenInference 则更强调语义约定：哪些字段叫 input、output、retrieval documents、tool call、LLM model、session、conversation。没有这层约定，不同框架的 trace 只是形状相似的日志；有了语义约定，平台才可能把 LangChain、LlamaIndex、OpenAI、Anthropic、自定义 agent runtime 的事件放在同一个查询模型里。

六、常见误读：分数、trace 和人审都可能骗人

6.1 高平均分不等于可上线

平均分最容易掩盖长尾失败。一个 coding agent 在简单 bugfix 上从 82% 到 87% 的提升，可能同时让高风险命令误用从 0.5% 增加到 2%。如果 eval suite 没有按任务类型、风险等级、仓库规模、工具类型分层，你看到的是一个混合均值，不是上线证据。

更稳的做法是为不同 failure mode 建立单独 gate：任务成功率、危险工具调用、未授权网络、diff 面积、测试通过、成本预算、latency p95、恢复成功、用户可解释性。这些 gate 可以用同一批 trace 产生，但不应该被压成一个“智能程度总分”。

6.2 Trace 多不等于可观测

Trace 的价值来自低基数、可关联、可回放、可保护。如果每个 span 都塞 prompt 全文、工具输出全文、文件路径和用户标识，短期看似方便，长期会让存储、查询、权限和合规全部失控。OpenClaw 把 content capture 做成显式 opt-in，Claude Code 对 analytics metadata 做类型标记、sanitization 和 truncation，都是在保护这个边界。

6.3 LLM judge 不等于人类 reviewer

LLM judge 能稳定处理一部分 rubric，但它也会受 prompt、模型版本、temperature、输入顺序和上下文长度影响。人类 reviewer 则能处理业务语境和边界判断，但吞吐低、成本高、也会漂移。更好的结构是三层：deterministic scorer 先处理可执行事实，LLM judge 处理语义维度，人审抽样校准 judge 并处理高风险样本。

为什么不推荐一开始就上“全自动综合评分”

综合评分的问题不是数学上不能做，而是组织上太容易被误用。它把任务成功、成本、延迟、风险、体验、可维护性压到一个数字里，导致每次 regression 都要重新争论权重。早期更好的做法是保留多个清晰指标：哪些是 hard gate，哪些是 soft signal，哪些只用于趋势观察。等指标稳定后，再为特定发布决策设计加权分。

七、落地路线：从一个失败 trace 开始，而不是从平台采购开始

7.1 七站闭环

如果从零开始建设 agent evals and observability，最有效的路线不是先比较 20 个平台，而是从一个真实失败 trace 开始：

  1. Capture：拿到一次完整失败运行，包括用户输入、工具链路、模型调用、日志、token/cost、最终状态。
  2. Label：给失败打标签：任务理解、工具选择、权限、检索、上下文、输出格式、成本、恢复、产品体验。
  3. Replay：把它压成可复现 fixture。去掉一次性数据，保留最小必要上下文。
  4. Score：先写 deterministic scorer，再补 LLM judge 和 reviewer rubric。
  5. Gate：把高风险指标变成 CI 或 release gate，而不是只在 dashboard 里展示。
  6. Monitor：上线后看同类 failure mode 的频率、成本和 drift。
  7. Repair：失败修复后，把新 trace 回写到 golden traces，防止同类问题复发。

7.2 工具选择建议

当前痛点 优先工具 原因 不要先做什么
prompt 或模型替换经常回归 promptfoo、DeepEval、simple-evals 快速把矩阵测试和 scorer 放进 CI 不要一开始就建设完整 trace warehouse
RAG 回答不稳定 Ragas、DeepEval、Phoenix 先把 retrieval、context、faithfulness 分开测 不要只看 final answer 评分
生产 agent 失败不可解释 Langfuse、Phoenix、Opik、OpenLLMetry/OpenInference 先打通 trace、span、score、dataset 和 annotation 不要把 prompt 全文无边界写进 logs
provider 成本和请求日志失控 Helicone、Portkey gateway、TensorZero、OpenLIT、OpenTelemetry collector gateway 和 OTel 接入路径短，先解决 visibility、routing、guardrails 和成本归因 不要用人工 spreadsheet 追 token/cost
agent runtime 正在自研 自定义 rollout ledger + OTel + promptfoo/AutoEvals runtime-specific 事实必须自己拥有，再接平台 不要让平台数据模型倒逼 runtime 历史结构

八、可以迁移的工程规则

最后把整篇文章压成一组可执行规则。

规则 保护的 invariant 违反后的症状
先记录 runtime facts，再解释分数 失败可以回放和审计 eval 失败只剩一句“模型答错了”
trace、dataset、score 必须有稳定关联键 生产样本能转成回归用例 dashboard 和 CI 各说各话
内容采集默认关闭，必要时按字段打开 调试能力不变成泄露面 日志后端出现 prompt、路径、secret 或客户数据
用多 scorer，而不是一个万能 judge 可执行事实和语义判断分层 平均分上涨但风险和成本一起上涨
把失败 trace 升级成 golden trace 事故修复能进入长期记忆 同类 failure mode 在几周后复发
按赛道选工具，不按 star 盲选 工具解决正确层级的问题 用 eval runner 期待生产监控，或用 dashboard 期待 CI gate

真正成熟的 agent 质量体系，不是一个分数面板，也不是一个 trace 瀑布图，而是一套运行纪律：每一次真实失败都能被捕获、归因、脱敏、回放、评分、进入门禁，并在下一次部署后被继续观察。evals 让系统在已知任务上不退化；observability 让未知失败能变成下一批已知任务。两者合起来，agent 才有工程意义上的进步。
