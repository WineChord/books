Code Execution 的六层栈

模型负责提出意图，execution plane 负责把意图变成可审计、可取消、可恢复、可隔离的真实副作用。真正困难的部分，不是把一段命令跑起来，而是决定它能不能跑、在哪里跑、跑多久、输出多少、失败后还能不能解释。

先把证据边界说清楚

这篇文章按公开仓库和官方文档交叉验证。公开仓库的源码引用尽量固定到 commit SHA；产品行为只在官方文档或可见源码能支持时陈述；不可公开复核的实现观察不参与本文的公开结论。

本文的排序分两种。 流行度排序只看 GitHub metadata 在 2026-06-16 的快照，主要指标是 stars；能力排序按隔离边界、权限治理、环境广度、长任务生命周期、观测恢复和产品集成综合判断。stars 不是安全性、正确性或工程质量的证明。

主线项目是 Codex、Claude Code、OpenClaw 和 Hermes Agent。它们代表四类不同的执行哲学：Codex 把本地命令执行做成平台化执行平面；Claude Code 的公开文档展示了 Bash 工具、权限配置和 sandbox 体验如何进入产品交互；OpenClaw 把审批、网关和安全命令策略前置成操作员治理；Hermes Agent 把“在哪个环境执行”抽象成可切换的 backend，包括 Docker、Daytona、Modal、SSH、Singularity 和 local。

行业实践部分覆盖 OpenHands、SWE-agent、mini-SWE-agent、AutoGen、smolagents、Aider、Open Interpreter、Gemini CLI、Qwen Code、Daytona、E2B、Microsandbox，以及 Firecracker、gVisor、Kata、bubblewrap、firejail、nsjail 等底层隔离组件。这里的目标不是列百科，而是回答一个工程问题：当 agent 需要真正改文件、跑测试、开服务、读日志、调用工具时，execution plane 应该长什么样。

一个可用的六层模型

Code execution 可以拆成六层：第一层是模型意图，把“想做什么”表达出来；第二层是工具契约，用 schema、参数和命令形态限制意图；第三层是权限闸门，决定允许、询问、拒绝或收窄权限；第四层是沙箱边界，选择本机、容器、远端 workspace、微虚拟机或专用解释器；第五层是进程会话，负责 shell、PTY、代码解释器、后台任务和取消；第六层是观测账本，截断、流式传输、保存输出、记录错误，并支撑审计、重试和恢复。

这个模型能解释为什么最简实现看起来很短，却很快遇到工程极限。一个 subprocess.run 可以完成本地命令，但它通常没有细粒度权限、没有跨平台沙箱转换、没有长任务复用、没有增量输出、没有输出上限策略，也没有把用户审批和系统策略变成可复盘的记录。相反，一个成熟 execution plane 的代码量往往花在“边界”上：权限边界、状态边界、输出边界、时间边界和责任边界。

Codex：执行平面最完整的样板

Codex 的 Rust 实现把 code execution 拆得很干净。模型侧看到的是结构化工具调用；协议层有 AskForApproval 和 SandboxPolicy；core 层把 exec 参数、审批动作、超时、输出截断和捕获策略收拢；sandboxing crate 再根据平台把命令转换成 macOS seatbelt、Linux sandbox 或无沙箱执行。

在 process_exec_tool_call 这一段，可以看到它不是直接 spawn：先构造 request，再进入审批和 sandbox 决策，再执行并把输出变成协议事件。默认超时、输出 cap 和 drain timeout 也在同一个文件里显式定义。这种设计的好处是，每一次命令执行都处在同一条可审计路径上。

select_initial 和 transform 是 Codex execution plane 的中枢：前者选择初始 sandbox 类型，后者把“想执行什么”变成“在当前平台上如何受限地执行”。再往下看 permission profile intersection，Codex 不是让请求覆盖授权，而是把请求权限和已授予权限求交集。这是安全系统常见的好味道：更具体的请求只能收窄边界，不能扩大边界。

另一个容易忽略的点是输出。Codex 的 ExecToolCallOutput 把 stdout、stderr、aggregated output、exit code 和 duration 都变成结构化结果；exec server 还有 replay buffer 和 live fanout。对 agent 来说，输出不是打印给用户看的日志，而是下一步推理的输入，必须有上限、有增量、有恢复。

Claude Code：把 Bash 工具产品化

Claude Code 的公开文档强调命令执行需要权限确认、可配置的工具权限和 sandbox 选项。因为本文不能给出可公开复核的 Claude Code 源码锚点，所以这一节只讨论公开文档能支撑的产品层设计，不把内部实现细节作为能力排序依据。

它最值得学习的是 Bash 工具被放在用户可理解的权限系统里：用户可以配置哪些工具默认可用，危险操作需要确认，sandbox 让命令执行从“全信任本机”退到一个更明确的风险边界。也就是说，Bash 不再是隐藏在 agent 背后的实现细节，而是产品界面和用户心智的一部分。

这种设计说明一件事：用户对“允许执行”的理解不是静态的。一个 git diff、一个 npm test、一个 curl、一个 rm 在风险上完全不同；同一个命令在只读目录、项目目录、家目录或网络可用环境里的风险也完全不同。所以成熟的 Bash 工具不应该只问“是否运行 shell”，而应该让用户看见命令意图、作用范围和可撤销程度。

OpenClaw：治理优先的执行系统

OpenClaw 把 code execution 放进一个更像“操作员控制台”的系统里。它明确避免在 argv-based 执行里默认开启 shell，需要 shell 时走显式 wrapper；runCommandWithTimeout 处理 cwd、env、timeout、no-output-timeout、abort signal、Windows 进程树终止和输出 decode；默认输出上限也在同一模块里被显式管理。

更有辨识度的是审批层。ExecHost、ExecSecurity、ExecAsk、ExecMode 把 sandbox、gateway、node、allowlist、deny、ask、auto、full 等策略维度显式建模。审批 payload 不是“同意或不同意”这么简单，还包含 system run plan、显示文案、socket/file 协调、目录权限和链接安全检查。

safe bin policy profiles 也很有价值：它把 jq、grep、sort、head、tail、wc 等常见命令归入更细的允许或拒绝策略。很多系统只区分“读命令”和“写命令”，但真实 shell 风险来自组合：find 可以遍历隐私路径，xargs 可以扩散副作用，curl 可以出网，sh -c 可以隐藏真实意图。OpenClaw 的价值在于它愿意把这些灰度细节做成可维护的策略资产。

Hermes Agent：环境路由和工具 RPC

Hermes Agent 的 code execution 不是只围绕一个本地 shell 展开，而是把终端和代码工具放进统一环境抽象。code_execution_tool.py 开头就说明了两种 transport：local UDS 和 remote file RPC。它还强调一个重要限制：远端工具调用结果不自动进入模型上下文，默认只返回 stdout。这会逼迫系统把“给模型看的观测”和“环境里真实发生的事情”区分开。

Hermes 的环境层更像一个 router。base environment 使用 spawn-per-call 模型，但维护 session snapshot 和 cwd tracking；wait/drain loop 处理 timeout、中断、子进程输出管道和 UTF-8 增量 decode；Docker backend 通过 cap-drop、no-new-privileges、pids limit、tmpfs、network none 做 hardening；Daytona backend 则负责 resume/create sandbox、同步文件、执行和 cleanup。

这条路线适合多环境 agent：同一套工具协议可以落到 local、Docker、Singularity、Modal、Daytona 或 SSH。它的强项不是单点最硬隔离，而是把 backend 切换、文件同步、凭据挂载、stdout/stderr 管理和终端生命周期收在一个抽象下面。

远端 workspace 与微虚拟机：OpenHands、Daytona、E2B、Microsandbox

当 agent 不只跑单条命令，而是要打开浏览器、启动服务、预览端口、保留 workspace、多人协作和跨会话恢复时，本地 shell 的模型就不够了。OpenHands 把 sandbox 看成会话对象：start sandbox、resume、pause、delete 都是 app server 的显式职责；conversation router 在发送事件前还会检查 sandbox 和 agent server URL，并带上 session API key。

Daytona 和 E2B 更像“agent 的执行云”。Daytona 的 process API 覆盖 code run、PTY session、shell session 和命令执行；sandbox API 覆盖创建、snapshot、SSH access、delete、fork 和 port preview。E2B 也提供面向 AI app 的云端 sandbox、process 和 file primitives。它们的共同点是把隔离和生命周期变成远端服务，而不是让每个 agent 自己维护容器细节。

Microsandbox 不属于同一类 hosted workspace service，它更靠近底层 microVM execution API。它的 ExecRequest 包含 cmd、args、env、cwd、user、tty、rows、cols 和 rlimits；VM config 覆盖 vCPU、memory、rootfs、mounts、env、workdir、exec 和 network；agentd session 再暴露 PTY、stdin/stdout/stderr 和 signal。它不是完整 coding agent，却非常适合做多租户 code execution 的安全 substrate。

框架路线：SWE-agent、AutoGen、smolagents

SWE-agent 的优势是把软件工程任务抽象成 shell session 加 observation template。communicate 负责命令交互，工具配置里有交互命令和独立命令的 blocklist，agent config 里有 timeout 和输出截断模板。它不是最强的产品执行平面，却非常适合 benchmark、研究和复现实验。

mini-SWE-agent 则走反方向：local environment 直接用 subprocess.run(shell=True)，设置 cwd、env 和 timeout，把 stdout/stderr 合并返回。它的价值在于把最小闭环暴露得非常清楚：如果你要教学、写实验或快速替换 execution backend，这种可读性比“大而全”更重要。

AutoGen 和 smolagents 更像框架级 executor。AutoGen 的 default executor 倾向优先使用 Docker，local executor 文档也明确提示本地执行风险；CodeExecutorAgent 只从 fenced code block 提取代码执行。smolagents 的 local Python executor 设置输出、操作数、循环和时间限制，也维护危险模块和函数列表；remote executor 覆盖 E2B、Modal、Docker 和 Wasm 等 backend。

本地 CLI 路线：Aider、Open Interpreter、Gemini CLI、Qwen Code

Aider 的 shell 设计很直接：有 TTY 时选择 pexpect，否则使用 subprocess，输出按字符流式返回。这很适合个人开发中的“跑测试、看失败、改代码、再跑测试”循环，但安全边界主要来自用户所在环境和用户自己的判断。

Open Interpreter 更强调多语言解释器。它的 terminal 会按语言管理 active process 并流式输出；subprocess language 层负责启动解释器、重试和读取输出。这类系统的价值是“能控制本机”，风险也来自同一件事：本机就是边界。

Gemini CLI 和 Qwen Code 展示了现代 coding CLI 的另一种收敛。Gemini SDK 的 AgentShell 通过 shell tool、confirmation 和 ShellExecutionService 执行命令；Qwen Code 的 PermissionDrawer 至少能证明它把 Bash command approval 暴露成明确 UI。这里的稳妥结论是：现代 CLI agent 已经不再把 shell 风险藏在实现里，而是越来越倾向把执行意图放到用户可确认的界面上。

底层隔离：不要把 Docker 当作安全答案的终点

许多 agent 项目默认把 Docker 作为第一层隔离，这很合理：它普及、可组合、开发体验好。但多租户 code execution 不能把“跑在容器里”直接等同于“安全”。隔离 substrate 大致可以按强度和成本排成阶梯：本地 subprocess 最轻也最危险；语言解释器限制适合 Python code agent；Linux namespace 工具如 bubblewrap、firejail、nsjail 更贴近进程 jail；Docker 和 gVisor 改善容器边界；Kata 和 Firecracker 把 VM 或 microVM 引入边界；Hosted sandbox 再把生命周期、网络、存储和审计做成服务。

工程上真正要问的是三件事：第一，攻击者模型是谁，是自己的模型误操作，还是不可信用户提交任意代码；第二，副作用面在哪里，是文件系统、网络、凭据、GPU、内网、浏览器还是长跑服务；第三，失败时是否能快速销毁和复原。如果这三个问题没有答案，换成更“硬”的隔离技术也只是把风险推迟暴露。

设计一套 execution plane 的原则

1. 权限要描述能力，不要只描述命令字符串

grep、cat、python、node、sh -c 都不是天然安全或危险。权限策略应该关注能力：读哪些路径、写哪些路径、能不能出网、能不能读环境变量、能不能启动后台进程、能不能打开端口、能不能访问凭据、能不能跨 workspace。命令字符串只能作为策略输入之一。

2. 审批应该收窄权限，而不是临时放大全局权限

Codex 的 permission profile intersection、OpenClaw 的 exec mode、Claude Code 的 Bash permission flow 都在解决同一件事：模型请求和用户授权必须相交。用户同意跑一次测试，不等于同意后续所有 shell 命令；用户同意读项目目录，不等于同意读家目录和系统密钥。

3. stdout 不是审计日志

给模型看的输出需要截断、摘要和去噪；给用户看的日志需要可解释；给审计看的记录需要完整、结构化、带时间和环境信息。把三者混在一起，会同时损害推理质量、用户体验和安全追踪。

4. 长任务需要进程身份、取消和 replay

真实项目里的 npm install、测试套件、dev server、容器 build、模型下载都可能超过一个模型回合。没有 process id、session id、cancel signal、output replay 和 resource cleanup，agent 很容易留下失控任务或丢失关键输出。

5. 环境状态必须显式

cwd、env、PATH、依赖缓存、挂载目录、网络策略、端口映射、用户身份、session snapshot 都是执行语义的一部分。成熟系统会把这些状态显式建模；简陋系统则让它们散落在 shell 进程里，最终只能靠猜。

6. 沙箱失败要 fail closed

如果系统本来应该进入 sandbox，却因为平台缺依赖、权限不足或策略转换失败而退回裸执行，那就是最危险的故障模式。更好的行为是拒绝执行、解释原因、给出可恢复操作，或要求用户显式切换到较低安全等级。

怎么选：按风险和产品形态选择

你的场景 优先看 原因
本地 coding agent，需要改仓库、跑测试、给用户审批 Codex、Claude Code、Gemini CLI、Qwen Code 工具调用、审批和本地沙箱路径最接近用户日常开发。
企业内 agent，需要网关、节点执行和命令治理 OpenClaw 它把审批、执行宿主和 safe command policy 做成系统边界。
需要跨 Docker、云 sandbox、SSH、Modal 等环境切换 Hermes Agent 环境路由和工具 RPC 是核心设计目标。
浏览器里的远端软件工程 agent OpenHands、Daytona、E2B workspace 生命周期、端口预览、恢复和协作比单命令更重要。
研究、benchmark、课程或快速原型 SWE-agent、mini-SWE-agent、AutoGen、smolagents 框架和最小实现更容易改造，也更容易解释实验结果。
不可信用户提交任意代码，多租户执行 Microsandbox、Firecracker、gVisor、Kata、nsjail 此时 agent 体验不是第一优先级，microVM、系统调用边界和资源限制才是。
个人本地自动化和解释器式交互 Aider、Open Interpreter 简单、直接、反馈快，但要清楚它们默认更依赖本机信任边界。

结论：execution plane 是 agent 的可信边界

Code execution 的成熟度，决定了 agent 能不能从“会说怎么做”变成“能安全地做”。最小实现可以是一行 subprocess；生产实现却必须面对权限、沙箱、长任务、输出、恢复、审计、远端 workspace 和底层隔离。Codex 展示了协议化和平台 sandbox 的清晰边界；Claude Code 展示了 Bash 工具产品化；OpenClaw 展示了治理优先；Hermes 展示了多环境路由；OpenHands、Daytona、E2B 和 Microsandbox 展示了远端 sandbox 与微虚拟机 substrate；SWE-agent、AutoGen、smolagents、Aider、Open Interpreter 则给出了从研究框架到本地实用工具的完整光谱。

最终判断一个 code execution 系统，不要只问“它能不能运行命令”。更好的问题是：它能不能解释为什么允许运行；能不能把允许范围限制到最小；能不能在正确的环境运行；能不能控制时间、输出和资源；能不能恢复和审计；当沙箱不可用时，能不能拒绝冒险。这些问题的答案，才是 agent 工程里真正的分水岭。
