Sandbox 不是一个开关：AI Agent 如何获得可执行的边界

如果一个 AI Agent 能读文件、写代码、跑命令、开浏览器、访问网络，它就不再只是“会说话的软件”。它开始拥有真实的系统权限。Sandbox 的核心问题不是“有没有隔离”，而是：谁制定策略，谁投影文件和网络，谁承受逃逸风险，谁负责生命周期和审计。

写作快照：2026-06-16 主线：Codex / Claude Code / OpenClaw / Hermes 排名指标：GitHub stars 与能力包络分开

本文把 sandbox 拆成工程上可验证的几层：Agent 里的权限策略，运行前的文件和网络投影，Linux/容器/VM 级执行边界，以及面向 AI workload 的创建、快照、恢复、观测和计费能力。这样讨论才不会把 “Bash 需要审批” 误当成 “Bash 已经隔离”，也不会把 GitHub stars 误当成安全证明。

本文的中心判断：AI Agent 的 sandbox 不是单点功能，而是一条供应链。策略越靠上，越适合表达意图；边界越靠下，越接近安全保证；平台越完整，越能服务真实 Agent 工作流，但也越需要检查它到底把隔离交给了谁。

一、先把 sandbox 说清楚

“Sandbox” 在不同团队嘴里常常指三种东西：命令审批、进程限制、远端临时环境。它们都重要，但不是同一种边界。

最容易出错的说法是“这个 Agent 有 sandbox，所以安全”。更准确的问法应该是：这个 Agent 的 sandbox 是什么威胁模型下的 sandbox？它防的是误删文件、越权读写、网络外传、系统调用逃逸、内核攻击面，还是多租户之间的横向移动？

一个简化的风险式子是 \(R \approx U \times A \times E\)：\(U\) 是输入或代码的不可信程度，\(A\) 是进程握有的主机权限，\(E\) 是逃逸面。提示词、审批和工具规则主要降低“被允许做坏事”的概率；namespace、seccomp、gVisor、microVM 和硬件虚拟化主要降低“即使做了也能伤到哪里”的范围。

这也是为什么 bubblewrap README 明确把自己定位为底层构造工具，而不是完整安全策略；为什么 gVisor README 要强调它不是普通 syscall filter，也不是传统 VM；为什么 Firecracker README 从一开始就把目标放在多租户、低开销的 microVM 上。

二、四平面模型：不要把策略、投影、边界和生命周期混在一起

Policy Plane：决定“是否尝试”

Policy Plane 是权限规则、审批缓存、命令分类器和组织级配置。Codex 的执行工具会围绕审批缓存、sandbox 尝试、是否需要 escalated permissions 做决策；相关逻辑集中在 with_cached_approval、权限升级与 sandbox 选择、以及 SandboxAttempt 这几个区域。

Policy Plane 负责表达“我愿意让这个命令访问网络吗”“这个路径可以写吗”“失败后能不能重试”。但它不是 OS 边界。命令一旦在主机上无隔离运行，策略错误、解析绕过、环境变量继承、shell 展开和工具链副作用都会回到主机权限模型里。

Projection Plane：决定“它看见什么”

Projection Plane 把宿主机投影成一个更小的世界：哪些目录只读，哪些目录可写，哪些网络目标可出站，哪些 Unix socket 可以碰，临时目录在哪里。Codex 的 ExecRequest 会携带命令、工作目录、环境、sandbox 类型、文件系统策略和网络策略；Linux 侧再由 codex-linux-sandbox 将这些策略落到 bubblewrap 和 seccomp 组合上。

投影不是隔离强度本身，但它决定 blast radius。一个只读源码树加可写临时目录，和把整个 home 目录挂进去，是完全不同的 sandbox。

Execution Boundary：决定“逃逸要打穿什么”

Execution Boundary 才是最接近传统安全意义的 sandbox：Linux namespace、cgroup、rlimit、seccomp、Landlock/LSM、macOS Seatbelt、Windows AppContainer 或虚拟化边界。这里要问的是：不可信代码能不能直接调用宿主内核？能不能复用宿主网络命名空间？能不能挂载宿主敏感路径？能不能用容器特权或 runtime socket 跳出边界？

这也是 gVisor、Kata 和 Firecracker 的分野：gVisor 在容器和宿主内核之间放一个用户态 application kernel；Kata 把容器放进轻量 VM；Firecracker 直接提供面向 serverless 和容器 workload 的 microVM VMM。它们解决的问题不是“用户是否点了允许”，而是不可信 workload 真正运行时共享了多少宿主内核面。

Lifecycle Plane：决定“它怎么成为产品”

Agent 需要的不只是启动一个受限进程。真实工作流还需要模板、创建、命令执行、文件桥、端口映射、网络策略、浏览器或 GUI、快照、恢复、日志、配额和清理。E2B、OpenSandbox、CubeSandbox、Daytona、Microsandbox 这类项目的价值主要在 Lifecycle Plane：它们把底层边界包装成 Agent 可消费的运行时。

因此，能力排名要同时看隔离强度和产品完整度。一个 Firecracker microVM 很强，但它不是完整 Agent 平台；一个托管 sandbox SDK 很好用，但你仍然要知道它的底层边界、网络默认值和数据保留模型。

三、四个 Agent 主线：真正的分歧在“谁拥有边界”

Codex：把 PermissionProfile 编译成平台 sandbox

Codex 的思路是把“权限配置”变成平台执行请求，而不是把 shell 审批当成最终边界。公开源码里，ExecRequest 会承载命令、工作目录、环境、sandbox 类型、文件系统策略和网络策略；sandbox 请求转换 里会在网络禁用时注入 CODEX_SANDBOX_NETWORK_DISABLED，在 macOS Seatbelt 模式下注入 CODEX_SANDBOX=seatbelt。

Linux 路径更直接：landlock.rs 的注释把默认组合写得很清楚：用 bubblewrap 做文件系统隔离，用 seccomp 做网络限制。换句话说，Codex 的重点不是“一个神奇 sandbox”，而是把同一个权限语义映射到 macOS、Linux、Windows 的不同系统边界上。

值得注意的是，Codex 也把“能否绕过 sandbox”纳入策略判断。执行策略 会区分 denied reads、escalated permissions 和网络策略。这个设计告诉我们：如果用户显式声明某些路径不能读，就不能因为命令需要升级权限而顺手变成无边界执行。

Claude Code：公开配置显示 Bash sandbox 是一个受管设置域

Claude Code 的公开仓库不是完整实现源码，但它给出了企业配置和 changelog 证据。settings 示例说明 明确列出 settings-bash-sandbox.json 这一类配置，并提醒 sandbox 属性只适用于 Bash tool，不适用于 Read、Write、WebSearch、WebFetch、MCP、hooks 或内部命令。

示例配置本身也很有代表性：

{
  "allowManagedPermissionRulesOnly": true,
  "sandbox": {
    "enabled": true,
    "autoAllowBashIfSandboxed": false,
    "allowUnsandboxedCommands": false,
    "network": {
      "allowedDomains": []
    }
  }
}

这不是完整实现，但足以说明 Claude Code 把 Bash sandbox 作为受管配置域来治理。changelog 也能看到它在权限解析和 sandbox 规则上持续修补边界：例如 PowerShell 路径切换导致的越界读取和 git worktree 写 allowlist 过宽，见 2.1.149 相关修复；Linux/WSL 自定义 bwrapPath 与 socatPath 见 2.1.133 记录；allowManagedDomainsOnly / allowManagedReadPathsOnly 的优先级问题见 安全修复记录。

这里的工程教训很具体：命令解析、工作目录跟踪、网络 allowlist、受管配置优先级都会影响 sandbox。只要上层解析器和下层边界之间有不一致，Agent 就可能以为自己在沙箱里，实际却把权限投影错了。

OpenClaw：把 sandbox 放进网关和 Docker 后端策略

OpenClaw 更像一个带网关的个人 Agent 系统。它的安全文档把默认 sandbox 后端写成 Docker，并提供 session/workspace 级隔离、额外挂载、工具提权等配置语义；关键段落见 gateway security 文档。它的 Dockerfile 也体现了运行期姿态：可选安装 Docker CLI 是为了管理 sandbox 容器，运行用户切到非 root，并在 启动网关前 明确默认绑定回环地址。

OpenClaw 的价值在于把 Agent 策略、网关、容器后端和 workspace 访问模式连成一条线。但 Docker 作为默认后端时，要非常认真地检查：是否允许 host network、是否挂载 Docker socket、是否允许加入宿主命名空间、是否有特权容器、是否有 unconfined seccomp/AppArmor、额外挂载是否越过项目边界。

Hermes Agent：把“OS 级隔离才是边界”说得最直白

Hermes Agent 的 SECURITY.md 有一句非常适合做本文的分界线：面对 adversarial LLM，只有 OS-level isolation 是真正边界；审批、脱敏、工具 allowlist 都是进程内启发式手段。它还区分 terminal-backend isolation 和 whole-process wrapping：前者限制 shell/file 操作，后者才把 Agent Python 进程、代码执行、MCP subprocess、plugins、hooks、skills 等路径一起放进外层边界；见 相关段落。

Hermes 的 Docker 环境实现也体现了这个观点。基础安全参数 把 capability drop、no-new-privileges、PID 限制和 tmpfs 纳入容器启动参数；环境类说明 则把容器本身称为 security boundary，并说明 workspace 可写。它还提供 Daytona、Modal 这类远端环境后端，意味着“跑命令”不是唯一危险路径，代码执行工具和远端 sandbox 也要纳入同一个信任模型。

这给 Agent 设计一个很强的提醒：如果模型能生成 Python 并在宿主进程里执行，那么只 sandbox Bash 远远不够。只要存在另一个本地代码执行通道，攻击者就会走那个通道。

四、Linux 本地沙箱：bubblewrap、Firejail、nsjail 的分工

bubblewrap：低层投影器，适合被上层产品编排

bubblewrap 的定位非常清楚：它是 Flatpak 等系统使用的低层无特权 sandboxing 工具，主要依赖 user namespace 等内核特性。它会创建新的 mount namespace，并允许调用方选择 bind mount、tmpfs、只读路径、网络 namespace、PID namespace 和 seccomp filter；见 选项概览。

优点是小、直接、适合被 Codex 或 Claude Code 这种上层工具当作投影器；缺点也是它的优点：它不替你设计完整安全策略。你传错参数，它就会忠实构造一个错误的世界。

Firejail：面向桌面和常见应用 profile 的便利层

Firejail 把 Linux namespace、seccomp-bpf、capability、profile、SELinux/AppArmor/cgroup 等组合成更贴近日常应用的 sandbox 工具。它有大量 profile，适合“把某个本地应用关小一点”的场景。

对 AI Agent 来说，Firejail 的便利性不如 bubblewrap 那样容易嵌进精确投影，也不如 nsjail 那样偏竞赛/服务端隔离，但它展示了一个重要方向：sandbox 需要 profile，否则每次手写参数很难保持一致。

nsjail：偏服务端和评测环境的硬核拼装

nsjail 面向 Linux process isolation，组合 namespace、rlimit、seccomp-bpf、Kafel、chroot/pivot_root、只读挂载、网络和 cgroup。它很适合在线判题、CTF、批量运行不可信命令、评测 agent patch 的场景。

nsjail 的优势是控制面细，尤其在资源限制和 seccomp policy 上更适合服务端。代价是配置复杂，产品化时仍然要自己做文件桥、生命周期、审计、队列、网络策略和错误恢复。

五、容器隔离阶梯：runc 不是终点，gVisor/Kata/Firecracker 是不同答案

runc / containerd / Moby：容器生命周期，不等于 hostile code sandbox

runc 是按 OCI spec spawn/run containers 的 CLI；containerd 管完整容器生命周期；Moby 是组装容器系统的组件集合。它们是现代部署的基座，但“容器”默认仍共享宿主内核。

所以，Docker sandbox 要看具体配置：rootless、capability、seccomp profile、AppArmor/SELinux、只读 rootfs、挂载白名单、网络命名空间、cgroup、PID 限制、runtime socket 是否暴露。只说“在 Docker 里跑”没有安全含义。

gVisor：把 syscall 面收窄到用户态 application kernel

gVisor 提供一个用户态 application kernel，通过 runsc 与 Docker/Kubernetes 集成。它的关键价值是减少 workload 直接接触宿主内核的 syscall 面。

gVisor 很适合多租户容器、CI、在线执行和不可信但需要 Linux 兼容性的 workload。它通常比普通 container 强，但不等于完整 VM；兼容性和性能也要按 workload 测试。

Kata Containers：用轻量 VM 承载容器语义

Kata Containers 的目标是让 workload 像容器一样运行，但获得 VM 的隔离优势。其架构文档进一步说明 runtime、shim、hypervisor、guest agent 和 pod VM 的关系；见 architecture。

对 Kubernetes 平台来说，Kata 的吸引力在于把 VM 隔离塞进容器编排模型。代价是启动、镜像、存储、网络和观测链路都更复杂。

Firecracker：microVM 原语，不是完整 Agent 平台

Firecracker 是面向 serverless 和容器 workload 的安全快速 microVM。它通过 KVM 提供虚拟化边界，并在 内置能力 中包括 seccomp 和 jailer。

Firecracker 很适合作为 AI sandbox 平台的底层隔离原语，但它本身不替你做 Agent API、文件桥、浏览器、快照产品语义、权限审批和计费。CubeSandbox、Microsandbox、OpenSandbox 这类项目的意义，正是把 microVM 变成 Agent 能用的运行时。

六、AI sandbox 平台：真正的竞争在生命周期、兼容性和默认安全

E2B：Agent-facing cloud sandbox 的标杆接口

E2B 把自己定位为给 AI-generated code 运行的安全隔离云 sandbox，并提供 JS/Python SDK。README 里的快速例子覆盖创建 sandbox、运行命令和 Code Interpreter；见 quickstart。

SDK 源码展示了更完整的产品面：Sandbox 能力包括 Linux OS、文件、命令、git、隔离代码和网络；pause 与 snapshot 则说明它已经不只是“跑一条命令”。

OpenSandbox：开放协议和运行时适配层

OpenSandbox 主打通用 AI sandbox 平台，支持多语言 SDK、协议、Docker/Kubernetes runtime、命令、文件、代码解释器、browser/desktop、出入站策略，并在文档中列出 gVisor、Kata、Firecracker 等强隔离运行时。

它的价值是开放抽象和集成面，尤其是 MCP server 让 Claude Code、Cursor 等工具直接创建 sandbox、运行命令、读写文件；见 MCP 部分。但 OpenSandbox 的隔离强度取决于你配置的 runtime：runc、gVisor、Kata、Firecracker 是完全不同的威胁模型。

CubeSandbox：KVM microVM、E2B 兼容和快照能力

CubeSandbox 把自己定位为基于 RustVMM/KVM 的 AI Agent sandbox，强调单机/集群、E2B SDK 兼容、低延迟和低内存开销。它的亮点还包括资源池、快照克隆、CoW、独立 guest OS kernel、eBPF 网络和事件级回滚；见 核心特性。

这里要把“项目自述指标”和“外部验证”分开。CubeSandbox 的能力包络很强，特别适合自建 KVM 环境下追求 microVM 隔离、并发和 E2B 兼容的团队；但启动延迟、内存开销和生产成熟度需要在自己的 workload 上复测。

Daytona：把 sandbox 升级成完整开发环境运行时

Daytona 的定位是运行 AI-generated code 和 Agent workflow 的安全弹性基础设施，强调 dedicated kernel、filesystem、network、vCPU、RAM、disk、OCI/Docker 兼容和 stateful snapshots。它更像“完整开发环境运行时”，而不是单个隔离原语。

如果你的 Agent 需要长生命周期环境、工作区复用、团队化控制面、hybrid compute 和平台运维，Daytona 的产品面会比裸 Firecracker 或 nsjail 贴近业务。相应地，你也要检查 control plane、daemon、runner、snapshot manager、proxy 和网络边界。

Microsandbox：本地可嵌入 microVM 的轻量路线

Microsandbox 面向把 untrusted workload 放进快速本地 microVM。它强调硬件隔离、OCI images、Docker-like workflows、可嵌入 SDK、secrets、长任务和 Agent readiness。README 也说明它处在 beta 阶段，并支持 Linux KVM 或 macOS Apple Silicon；见 requirements。

Microsandbox 适合“我不想先建一整套云平台，但想把本地 Agent 的执行边界从进程/容器提高到 microVM”的场景。限制是生态和生产验证仍在增长期。

Deno / Wasmtime：语言级隔离是旁支，不是任意 shell 的替代品

Deno 是带 secure defaults 的 JavaScript/TypeScript/WebAssembly runtime，例如运行网络服务要显式 --allow-net。Wasmtime 则强调 WebAssembly runtime 的安全、fuzzing、防御纵深和 WASI 能力。

它们非常重要，但不应和 “run arbitrary Linux shell” 混成一类。语言 runtime 适合把可执行面限制在某个语言或 WASI 能力模型里；如果 Agent 需要跑任意包管理器、编译器、浏览器和系统命令，仍然需要进程、容器或 VM 级边界。

七、严格排序：先按流行度，再按能力和隔离强度

Agent 平台能力排名：看完整工作流，而不是裸边界

能力包络 项目 适合场景 为什么排在这里 需要复核
1CubeSandbox自建 KVM、追求 microVM 隔离、并发、快照克隆和 E2B 兼容。项目自述的能力包络最强：KVM、专用 guest kernel、CoW、快照/克隆/回滚、eBPF 网络、E2B SDK 兼容。项目自述性能指标、x86_64 Linux/KVM 约束、生产成熟度。
2E2B希望快速接入云端 AI code sandbox、SDK、文件、命令、网络、快照。Agent-facing API 成熟，开发者体验强，生命周期能力完整。底层隔离实现细节、数据驻留、成本、企业网络策略。
3Daytona完整开发环境、长期工作区、混合部署、团队级控制面。平台完整度高，覆盖 dedicated resources、OCI/Docker、snapshots 和控制/计算平面。你的 workload 是否需要完整环境，而不是更小的 sandbox。
4OpenSandbox需要开放协议、MCP、多 SDK、Docker/Kubernetes、可选强隔离 runtime。抽象层和适配面广，可以把 gVisor/Kata/Firecracker 等挂到统一 API 后面。实际 runtime 配置决定隔离强度，默认值必须审计。
5Microsandbox本地嵌入式 microVM，不想先部署完整平台。路线清晰，适合把本地 Agent 执行边界提升到 microVM。Beta 状态、生态成熟度、平台兼容性。
6gVisor / Kata / Firecracker你要自己搭平台，只需要核心隔离 runtime。隔离能力强，但不是完整 Agent 产品。文件桥、模板、快照、API、清理、审计都要自建。
7bwrap / nsjail / Firejail本地 CLI、评测、短命令、低延迟批处理。小而硬，适合被 Codex/Claude 这类上层工具编排。策略配置、资源限制、网络外传和宿主内核共享。

这个能力排名的前提是“AI Agent 要运行真实命令、读写文件、可能需要网络和快照”。如果你的 workload 只是运行受限 JS/TS 或 WASM 组件，Deno/Wasmtime 的语言级能力模型可能更合适；如果只是企业内部可信脚本，审批和 bwrap 可能已经足够。

八、选型地图：从威胁模型出发

五条实际规则

  1. 只要有不可信代码，就不要把审批当边界。审批是必要控制点，但真正的边界要落到 OS 或虚拟化。
  2. 本地单用户 CLI 优先从 bwrap/nsjail 开始。它们足够轻，能把文件和网络投影做小，适合低延迟命令。
  3. Docker 要先审配置，再谈 sandbox。禁用特权、runtime socket、host network、host PID、过宽挂载和 unconfined profile 是底线。
  4. 多租户或 adversarial workload 直接考虑 gVisor/Kata/Firecracker/microVM。共享宿主内核的容器不该作为唯一防线。
  5. 如果 Agent 需要模板、快照、浏览器、文件桥、日志和配额，买或构建平台，不要只买一个 runtime。否则你会在生命周期平面补大量胶水代码。

常见误读

误读 为什么错 更准确的说法
“有 Docker 就安全”默认容器共享宿主内核，且配置可以极大改变边界。Docker 是封装和生命周期工具，安全性取决于 runtime、profile、挂载、网络和权限。
“命令通过审批就是 sandbox”审批只影响是否执行，无法限制执行后能调用的系统能力。审批是 Policy Plane，sandbox boundary 是 Execution Boundary。
“禁止网络就没有外传”本地文件、socket、日志、构建缓存、DNS、包管理器和后续人工复制都可能形成路径。网络策略要配合文件投影、环境变量清理、日志审计和最小凭证。
“microVM 永远最好”强隔离带来启动、镜像、快照、观测和成本复杂度。按威胁模型选择；可信批处理不必一律上 microVM。
“stars 多就是安全”stars 反映关注度、生态和传播，不反映隔离边界。stars 和能力排序必须分开看。

给 Agent 团队的落地清单

  • 写出 threat model：谁不可信，能提交什么，最坏能拿到什么宿主权限。
  • 列出所有代码执行通道：Bash、Python、Node、MCP server、hooks、plugins、browser automation、package manager。
  • 把每个通道映射到同一个 sandbox 策略，不要只包 shell。
  • 默认只挂载工作区；凭证、SSH agent、Docker socket、云 metadata、home 目录都要显式拒绝。
  • 网络默认 deny，再按域名、端口、代理、包源和内网目标逐项允许。
  • 保留可审计日志：策略决策、实际命令、挂载、网络规则、sandbox ID、快照 ID、退出码和清理结果。
  • 用恶意 fixture 测试，而不只跑 happy path：路径穿越、shell 展开、环境变量注入、软链接、git hook、package script、socket、后台进程和大输出。
