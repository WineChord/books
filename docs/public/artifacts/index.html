Artifacts：AI Agent 如何把聊天变成交付物

这篇文章讨论的 artifacts，不只指 Claude.ai 里那种可以单独打开的可视化窗口。更宽一点看，artifact 是 agent 工作过程中产生的、可以被预览、恢复、编辑、复用、导出、分享或再次喂回模型的交付物。它可能是一段 HTML、一个 React 组件、一张图、一个表格、一份文档、一次命令输出、一个补丁、一个文件树、一个沙箱里的运行结果，也可能是协议流里一个带版本、带 MIME、带 owner 的对象。

如果只把 artifact 理解成 UI 组件，很容易低估它的工程难度。真正困难的地方不在“把代码放进 iframe”，而在十个更底层的问题：谁拥有它？什么时候生成？生成过程中能不能流式更新？模型下一轮还能不能看到？用户能不能编辑？编辑后是否形成新版本？预览代码跑在哪里？权限怎么隔离？会话恢复后路径还有效吗？最终能不能导出、发布或共享？

本文以四条源码主线为骨架：Codex、Claude Code / Agent SDK、OpenClaw、Hermes Agent。它们不是都把产物叫作 artifact，但都在处理同一类问题：agent 输出怎样从一次聊天里的临时文本，变成可追踪、可恢复、可操作的对象。

然后再把视角拉到热门开源实践：OpenWebUI、LibreChat、Vercel Chatbot、Open Canvas、E2B Fragments、Google ADK、A2A、AG-UI。这些项目分别代表产品 canvas、沙箱底座、agent 文件系统和协议层四种方向。

证据边界。表格里的 GitHub star 来自 2026-06-16 的 GitHub API 查询，适合表示当时的开源可见热度，不表示生产采用率或设计质量。Claude Code 的源码级讨论引用固定 commit 的公开源码镜像；Claude 产品 Artifacts 行为只引用 Anthropic 帮助中心和官方文档。其他源码链接都固定到本文调研时的 commit。

一、为什么 artifact 不是一张卡片，而是一条生命周期

Artifact 的最小定义可以写成一句话：它是一个有身份、有类型、有归属、有生命周期的 agent 产物。这个定义故意不把 artifact 绑定到某个 UI，因为同一个产物在不同系统里会落在不同层级。

在 Claude.ai、OpenWebUI、LibreChat、Vercel Chatbot 这类产品里，artifact 通常是聊天之外的一块工作区：右侧画布、独立窗口、版本页、复制下载按钮、预览 iframe、编辑器或 diff 模式。用户会直觉地把它理解成“模型做出来的一件东西”。

在 Codex、Claude Code、Hermes 这类 coding agent 里，artifact 更常表现为文件 diff、命令输出、持久化 tool result、截图、图片生成结果、补丁、checkpoint、文件树或 sandbox 里的临时文件。它不一定有漂亮的 canvas，但它必须能被 resume、rollback、inspect 或继续修改。

在 A2A、ADK、AG-UI 这类协议或 SDK 里，artifact 又变成了更抽象的 contract：一个 task 可以产生 artifact；artifact 可以有 parts；更新可以是 append，也可以标记 last chunk；artifact service 负责 Save、Load、List、Versions；UI 协议负责把 agent 事件变成前端可渲染的状态。

1.1 五层 artifact 栈

要避免概念混乱，最有用的分层是下面这五层：

层级 典型对象 核心问题 代表实现
流式生成层 delta、chunk、tool args、partial document 用户是否能看到产物逐步成形，失败时是否能保留半成品 A2A artifact update、Vercel data stream、Open Canvas graph state
会话项目层 message item、thread item、document id、artifact id 产物是否能被定位、引用、重放、恢复 Codex ThreadItem、Vercel UIArtifact、LibreChat artifact block
持久化层 文件、数据库记录、版本、checkpoint 产物是否跨轮次、跨会话、跨设备仍然存在 Claude Code tool-results、Hermes checkpoint、ADK artifact service
执行预览层 iframe、Pyodide worker、container、preview URL 不可信代码在哪里运行，权限、网络、资源和清理如何控制 OpenWebUI iframe/Pyodide、E2B Fragments、Daytona、OpenSandbox
发布协作层 share link、public artifact、organization artifact、embed 产物能否从私有会话进入多人协作或公开分发 Claude published artifacts、OpenWebUI shared scopes、AG-UI app bridge

这五层不是每个项目都要全部实现。一个 terminal coding agent 可以没有发布层，但它不能没有可恢复的文件和命令产物；一个聊天产品可以没有容器级执行，但如果它允许 HTML/JS artifact，就必须认真处理 iframe sandbox 和 CSP；一个协议可以不负责 UI，但必须把 artifact 的 identity、parts、append、final 等语义说清楚。

1.2 Artifact 的生命周期

一个成熟 artifact runtime 通常会经历下面的状态机：

intent
  -> draft
  -> streamed update
  -> preview
  -> persisted version
  -> edited or regenerated
  -> exported, shared, or garbage-collected

这里最容易被忽略的是 draft 和 preview。模型生成 HTML 时，草稿内容不应该一开始就被当作可信应用；命令输出过大时，完整输出不应该直接塞回模型上下文；沙箱生成文件时，路径不能天然等同于可分享链接。真正可靠的实现，会在每一次状态转换上加 contract：MIME、owner、权限、版本、资源限制、清理策略和恢复方式。

1.3 三个常见误区

第一个误区是把 artifact 等同于“富文本消息”。富文本消息仍然依附聊天流；artifact 应该有独立身份。没有身份，就很难更新、引用、比较版本或授权。

第二个误区是把 artifact 等同于“文件”。文件是最常见的持久化形态，但不是完整语义。一次 artifact 更新可能包含多个 part：正文、图片、数据、URL、元信息。A2A 的 helper 就把 text、data、raw bytes、URL 都包装成 artifact parts，并允许通过 TaskArtifactUpdateEvent 增量更新。

第三个误区是把 artifact 等同于“代码执行”。代码执行只是 artifact 的一种能力。文档、表格、图像、报告、patch、测试日志都是 artifacts；其中有些永远不需要执行，但仍然需要版本、权限和恢复。

二、四条主线：Codex、Claude Code、OpenClaw、Hermes 怎样处理产物

这四个项目代表 agent runtime 里 artifact 的四种核心能力：线程事件投影、上下文减压与工具结果落盘、媒体桥和 live preview、沙箱文件与 checkpoint。它们的共同点是都不满足于“把模型输出显示出来”，而是把输出接入了运行时的恢复和操作系统边界。

2.1 Codex：artifact 是 typed thread item，而不是单一类名

Codex 源码里并没有把所有产物统一命名为 Artifact。它更像一个 typed thread item 系统：用户消息、agent 消息、reasoning、web search、image view、image generation、file change、MCP tool call、context compaction 都是 TurnItem 的变体。这里值得关注的是设计方向：产物不是一段不可结构化的 transcript，而是可以被客户端重放和渲染的 typed event projection。

例如，ImageGenerationItem 和 FileChangeItem 都是 thread item。前者有 status、revised prompt、result、saved path；后者有 changes、status、stdout、stderr。文件改动本身又被建模成 FileChange，区分 add、delete、update 和 move path。

Codex 的 app-server protocol 还把底层事件投影成客户端可消费的 thread items。item_builders.rs 的注释说得很清楚：core protocol events 保持通用，app-server protocol 决定怎样把这些事件展示为 ThreadItem。同一个文件里，patch begin/end 会构造成 ThreadItem::FileChange，exec begin/end 会构造成 ThreadItem::CommandExecution。

这对 artifact 设计的启发是：不要急着设计一个万能 Artifact 表。对于 coding agent，文件改动、命令执行、图片、MCP 工具调用、上下文压缩本来就是不同对象。统一的是它们都能进入 thread history，被 rebuild、resume、render，而不是统一成同一种 payload。

Codex 的特点

  • 强项：事件类型清晰，适合多客户端重放；文件改动、命令执行、图片生成都有结构。
  • 限制：它不是产品级 artifact canvas；对 HTML/React/表格这类产物的编辑预览，不是它的主设计目标。
  • 适用：需要把 agent 工作流变成可审计、可恢复、可协作的 coding thread。

2.2 Claude Code：大工具结果先落盘，再把引用留给模型

Claude Code 的可见源码里，最像 artifact substrate 的一块，是 large tool result persistence。toolResultStorage.ts 定义了 tool-results 子目录和 <persisted-output> 标签；PersistedToolResult 包含 filepath、original size、isJson、preview、hasMore。

关键点不是“输出太大就截断”，而是“完整输出变成文件 artifact，模型上下文里只保留可寻址引用和预览”。persistToolResult 会把文本或 JSON 写到 session-scoped 路径，并生成 preview；buildLargeToolResultMessage 则把路径和预览封装成模型能理解的替代消息。

在 query 主流程里，这个动作发生在 microcompact 之前。源码注释显示，applyToolResultBudget 先对工具结果做预算控制；随后才进入 snip、microcompact 和 context-collapse。同一段流程 还说明 collapse 是 read-time projection，summary 存在 collapse store，而不是直接把 REPL 全量历史抹掉。

这套机制给 artifact runtime 的启发非常直接：大产物不要靠“更长上下文”硬扛。它应该有一个 storage identity，并通过可读预览接回模型。否则一次测试日志、一次搜索结果、一次代码生成，就能把后续所有推理污染掉。

Claude Code 的特点

  • 强项：把长工具输出从上下文压力里解耦出来，兼顾恢复和模型可访问性。
  • 限制：本文使用的是公开镜像里的可见源码，不把它当作官方发行版承诺；Claude.ai 产品 Artifacts 的发布、分享和可视化能力需要按 Anthropic 帮助中心理解。
  • 适用：需要长时间运行工具、搜索、测试、构建，并希望保留完整输出的 agent runtime。

2.3 OpenClaw：媒体、附件和 live preview 是 artifact 边界

OpenClaw 的 artifact 味道不在一个单独的 Artifact 类里，而在媒体存储、附件解析和 live preview finalizer 之间。

src/media/store.ts 定义了 media 目录、默认 5MB 上限、2 分钟 TTL，以及一个很重要的权限边界：文件本身用较宽的 read mode 方便 Docker sandbox 访问，但包含目录仍然是 owner-only 的信任边界。随后，subdir、id 和 path 都做了防逃逸校验。

这不是普通上传逻辑，而是 agent artifact 必须具备的边界感。一个图片、文件或媒体 URL 一旦可以流入 sandbox，就会同时涉及 SSRF、路径穿越、文件权限、大小限制、TTL、cleanup 和 MIME 判断。

OpenClaw 的 outbound attachment 也体现了这个思路。resolveOutboundAttachmentFromUrl 会根据访问选项加载 web media，再保存为本地 outbound media，并返回本地 path 和 content type。它把外部 URL 转成受控本地产物，而不是把任意远程资源直接交给后续链路。

另一个关键点是 preview finalization。deliverFinalizableDraftPreview 包了一层 live preview finalizer：先发可最终化的 preview，最后要么编辑成 final，要么按普通消息交付。对 artifact 来说，这是很实用的抽象：用户应该看到产物流动，但最终状态必须收束成可引用对象。

OpenClaw 的特点

  • 强项：媒体和附件链路边界清楚，适合多通道 assistant；live preview 思路适合把草稿产物转成最终产物。
  • 限制：它更像 agent channel runtime，不是专门的 artifacts canvas 产品。
  • 适用：需要处理图片、文件、外部 URL、sandbox 访问和多通道消息的 personal assistant。

2.4 Hermes：工具结果、沙箱临时目录和 checkpoint 组成恢复层

Hermes 的 tool_result_storage.py 把大工具输出控制写成三层防线：工具自身上限、单个结果落盘、单轮 aggregate budget。它和 Claude Code 的思路相似，但强调写入 sandbox temp dir，使不同 backend 上的模型都可以通过 read file 访问完整输出。

实现里一个很工程化的细节是写入方式。_write_to_sandbox 通过 stdin 把内容写入 sandbox，而不是把大文本塞进命令参数。这样避免 Linux 单个 argv 元素长度限制。maybe_persist_tool_result 则在超过阈值时返回预览和路径引用，失败时才退回 inline truncation。

Hermes 的另一块 artifact 基建是 checkpoint。checkpoint_manager.py 用单个共享 shadow git store 做透明文件系统快照，触发点是写文件、patch、破坏性 terminal 等操作。它强调 dedup、per-project refs、独立 index、默认排除依赖和大二进制文件，并通过 prune / gc / size cap 做维护。

这说明 terminal agent 的 artifact 不只是“最终生成了哪个文件”。中间的工具输出、临时文件、工作区快照、回滚点，都是用户真正依赖的产物。没有 checkpoint，artifact 的编辑能力就缺一条关键后路。

Hermes 的特点

  • 强项：大输出落盘和 checkpoint 很扎实，尤其适合长任务、破坏性操作和多 backend sandbox。
  • 限制：产品级可视化 canvas 不是主轴，artifact 体验更多体现在文件和恢复能力。
  • 适用：需要可靠执行、回滚、保留工具输出的本地/远程 coding agent。

三、产品型 artifacts：OpenWebUI、Vercel Chatbot、LibreChat、Open Canvas

产品型 artifacts 的核心不是“能不能生成 HTML”，而是用户能不能在聊天之外持续工作。这里要看四个能力：专门的 artifact view、版本和编辑、预览安全、持久化和共享。

3.1 OpenWebUI：最像 Claude Artifacts 的开源产品面

OpenWebUI 的官方文档直接把 Artifacts 描述为受 Claude.ai 启发的功能，用于在聊天之外处理可复用的独立内容。README 也列出 Native Python Function Calling Tool 和 Persistent Artifact Storage：后者是 artifact 的内置 key-value storage API，支持 personal / shared scopes。

源码里，Artifacts.svelte 订阅 artifact contents，并在新内容增加时切到最新版本；HTML artifact 通过 iframe srcdoc 渲染，带 sandbox 属性，并通过 injectCsp 注入 CSP meta。

代码执行方面，OpenWebUI 还能在前端用 Pyodide worker 执行 Python。executePythonAsWorker 会根据 import 自动选择包，获取上传文件内容，再把 code、packages、files 发给 worker。这让它不仅能展示 artifact，还能让部分 artifact 在浏览器侧执行。

评价

OpenWebUI 的优势是产品完整度高：artifact panel、版本导航、iframe sandbox、CSP、Pyodide、持久化 storage 都覆盖到。它的风险也正来自能力丰富：一旦允许 HTML/JS、文件、Python、共享 scope，权限和资源边界就必须持续维护。作为 self-hosted 产品，它是本文调研里产品型 artifact 综合能力最强的一档。

3.2 Vercel Chatbot：把 artifact 抽象成 document handler

Vercel Chatbot 的实现很值得看，因为它没有把 artifact 写成一段 prompt hack，而是抽象成 document handler。createDocumentHandler 为不同 kind 提供 onCreateDocument 和 onUpdateDocument，并把生成内容保存成 document。当前 artifact kinds 包括 text、code、sheet。

模型侧通过工具创建产物。createDocument 要求模型指定 title 和 kind，并向 data stream 写入 kind、id、title、clear、finish 等事件；updateDocument 则先取 document，检查 user id，再调用对应 handler 重写。

前端的 UIArtifact 明确包含 title、document id、kind、content、visible、status、bounding box。组件通过 SWR 拉取 document versions，默认选最新版本；用户编辑时，前端会 POST 新内容，并用 debounce 管理保存；版本切换和 diff/edit 模式在 version handler 里处理。

评价

Vercel Chatbot 的强项是设计清晰：artifact = document + kind + handler + data stream + version UI。它很适合作为产品工程模板学习。限制是它本质是一个模板，部署者还要自己处理真实多租户、安全策略、执行环境和生产运维。

3.3 LibreChat：prompt-level artifact 协议加解析器

LibreChat 的 README 明确把 Artifacts 列进产品能力。它的 artifact prompt 定义了“什么内容适合 artifact”：独立、较长、用户可能修改或复用、可脱离对话使用。prompt 中的协议 用 :::artifact{identifier=... type=... title=...} 包裹内容，并支持 HTML、SVG、Markdown、Mermaid、React 等 MIME 类型。

更重要的是，LibreChat 不是只靠 prompt 文本。packages/api/src/artifacts/update.ts 定义 artifact block 的起止标记；findArtifactClose 会识别 artifact close 和 code fence 的边界，避免简单字符串搜索被代码块里的 ::: 干扰；findAllArtifacts 同时支持 message content parts 和 fallback text。

评价

LibreChat 的优势是兼容性和自托管生态：它把 artifact 作为聊天协议的一层，使不同模型都能生成可解析的 block。它的风险也在这里：prompt-level 协议必须靠解析器持续兜底，复杂 UI 和执行安全需要更多产品层约束。综合看，它是“通用聊天产品接入 artifacts”的代表实现。

3.4 Open Canvas：把 artifact 放进 LangGraph 状态机

Open Canvas 的定位更窄，但实现很干净。它把 artifact 放进 graph state，而不是只把它当成消息渲染。ARTIFACT_TOOL_SCHEMA 定义 type、language、isValidReact、artifact、title；generateArtifact 绑定 tool，让模型输出结构化 args，然后创建 ArtifactV3。

更新逻辑更能体现版本设计。updateArtifact 会读取当前 artifact、获取高亮代码片段、只重写选中区域附近的内容，再把新 content 追加到 contents 数组，并把 currentIndex 移到新版本。共享工具里的 getArtifactContent 则按 current index 取当前版本。

评价

Open Canvas 的强项是 artifact lifecycle 被纳入 agent graph：生成、局部更新、版本选择都是状态机的一部分。限制是类型范围较窄，生态热度也低于 OpenWebUI、LibreChat、Vercel Chatbot。但如果要学习“artifact 不是消息，而是 agent state”，它是很好的样本。

四、沙箱底座：artifact 能不能运行，取决于执行边界

只要 artifact 可以执行代码，它就从 UI 问题变成 sandbox 问题。这里的核心不是“能不能运行”，而是在哪里运行、怎样写入文件、怎样安装依赖、怎样返回 preview URL、怎样限制资源、怎样清理。

4.1 E2B Fragments：从生成片段到 sandbox preview URL

E2B Fragments 是“AI 生成应用 + 沙箱预览”这条路线的代表。Vercel 模板页也把它作为 open-source AI artifacts and code execution 模板推荐。

源码里，app/api/sandbox/route.ts 会按 fragment template 创建 E2B sandbox，写入生成的代码文件，必要时安装依赖。如果 template 是 code interpreter，就执行代码并返回 stdout、stderr、cell results；否则返回 sandbox id、template 和预览 URL。前端的 FragmentPreview 再按 template 类型选择 interpreter result 或 web preview。

这说明 E2B 这类项目不是 artifact UI 的替代，而是它的执行底座。OpenWebUI、Vercel Chatbot、LibreChat 可以决定怎么生成和展示；E2B、Daytona、OpenSandbox 负责让生成代码安全地跑起来。

4.2 Daytona、OpenSandbox：更通用的 agent execution substrate

Daytona 和 OpenSandbox 更像通用执行平台。Daytona 的仓库描述强调 secure and elastic infrastructure for running AI-generated code；OpenSandbox 的描述是 secure、fast、extensible sandbox runtime for AI agents。它们在 artifact 生态里的位置不是“某个聊天框里的卡片”，而是运行代码型 artifact 的隔离层。

这类 substrate 的能力排序不能只看 UI。更关键的是：是否支持多语言/多模板，是否能挂载文件，是否能提供预览 URL，是否能限制网络，是否能限制 CPU/内存/时长，是否有审计，是否能回收资源，是否能和 agent session 绑定。

4.3 沙箱不是可选项

如果一个产品允许模型生成 HTML、JS、Python、Shell、React 或依赖安装，却没有明确执行边界，那么 artifact 能力越强，风险越高。一个成熟的 artifact runtime 至少要回答：

  • 不可信代码是否永远运行在隔离环境里？
  • 预览 iframe 是否有 sandbox、CSP 和导航限制？
  • 上传文件、生成文件、外部 URL 是否做大小、MIME、路径和访问校验？
  • 执行结果是否有资源上限和超时？
  • 临时文件、preview URL、容器实例何时清理？
  • 用户编辑后的版本是否可回滚？

这些问题都不是前端体验细节，而是 artifact 能力能否进入生产环境的分界线。

五、协议层：避免 artifact 变成每家产品的私有方言

当 artifact 从单产品能力变成 agent ecosystem 的通用能力时，协议层会变得重要。否则每个前端、每个 agent、每个工具都会发明自己的 :::artifact、自己的 JSON、自己的 stream event，最后无法互操作。

5.1 A2A：task-owned artifact 和增量更新

A2A 直接把 artifact 放进 agent-to-agent 协议。Python helper 里的 new_artifact 创建带 artifact id、parts、name、description 的对象；text、data、raw、URL 都有 helper。更关键的是，TaskArtifactUpdateEvent 支持 append、last chunk 和 artifact id。

这套模型非常适合跨 agent 任务：artifact 不是 UI 里的孤立卡片，而是 task 的产物。接收方不必知道它最终会被渲染成 tab、文件还是通知，只要能按协议处理 parts 和 updates。

5.2 ADK：artifact service 是 agent 的文件记忆层

Google ADK Go 把 artifact 做成服务接口。artifact/service.go 明确说 artifact 是由 app name、user id、session id、filename 标识的文件，并支持 Save、Load、Delete、List、Versions；Service 接口 把这些能力固定下来。

内存实现里，Save 会为同名 artifact 递增 version；List 同时列出 session-specific 和 user-scoped artifacts；Versions 列版本。load_artifacts 工具 还能把可用 artifact 名称告诉模型，并要求模型需要时先调用工具加载内容；初始 instructions 明确要求访问 artifact 前先 load。

ADK 的价值在于它把 artifact 放进 agent runtime，而不是把它留给前端组件。文件记忆、版本、用户 scope、session scope 都是协议化对象。

5.3 AG-UI：artifact 的 UI 侧需要事件标准

AG-UI 的定位不是 artifact storage，而是 agent-user interaction protocol。README 说它是事件协议，agent backend 在执行中发出约 16 类标准事件，支持 SSE、WebSocket、webhook 等传输，并强调 bidirectional state synchronization、generative UI、structured messages 和 frontend tool integration。

这对 artifacts 很关键：如果 A2A 解决 task artifact，ADK 解决 artifact service，那么 AG-UI 解决“agent 产物如何进入用户应用”。其中 A2UI middleware 的测试显示，render_a2ui 可以在 tool args streaming 时发出 activity snapshot，并在 run finished 时合成 tool call result。这就是 UI artifact 需要的事件化能力。

5.4 MCP 是相邻层，不是 artifact 协议本身

MCP 很重要，但它解决的问题更偏“agent 怎么发现和调用外部工具、资源、提示模板”。它可以返回文件、资源 URI、tool result，也可以间接产生 artifact；但 artifact 的版本、编辑、预览、发布、UI 更新，不是 MCP 单独负责的完整语义。更稳的架构是：MCP 提供工具和资源入口，A2A / ADK / AG-UI 或产品自有协议承载 artifact 生命周期。

六、排序：按流行度和 artifact 能力分开看

用户真正做选型时，最容易犯的错是只看 star。star 代表开源可见热度，不等于 artifact 能力完整度。本文把排序分成两张表：第一张严格按 GitHub star 排，第二张按 artifact 能力排。能力判断采用分项矩阵，考虑显式 artifact model、流式更新、预览/执行、持久化/版本、编辑、协议互操作、安全边界、生产可用性。

6.3 最终选型结论

如果你要做一个面向用户的 AI 聊天产品，优先看 OpenWebUI、Vercel Chatbot、LibreChat、Open Canvas。它们直接回答“用户在哪里看、改、下载、切版本”。

如果你要做 coding agent，优先看 Codex、Claude Code、Hermes、OpenClaw。它们不一定给你一个漂亮 canvas，但会告诉你文件改动、命令输出、媒体、checkpoint、tool result 怎么变成可恢复对象。

如果你要让 artifact 运行代码，优先看 E2B、Daytona、OpenSandbox 这类 substrate，再把它们接到上层产品或 agent runtime。不要让前端 iframe 直接承担隔离责任。

如果你要做多 agent 或多前端互操作，优先看 A2A、ADK、AG-UI。artifact 的 identity、parts、updates、versions、UI events 应该协议化，而不是散落在 prompt 和私有 JSON 里。

七、设计 artifact runtime 时必须守住的十个不变量

综合这些实现，可以提炼出十个不变量。它们比“用哪套 UI 组件”更稳定。

7.1 身份：每个 artifact 都要能被引用

没有 id，就没有更新、版本、权限、导出和审计。Vercel 的 document id、A2A 的 artifact id、ADK 的 app/user/session/filename 组合、Codex 的 thread item id，都是在解决身份问题。

7.2 类型：MIME 和 kind 要比自然语言可靠

模型说“这是一个网页”不够。runtime 需要知道它是 text/html、image/svg+xml、text/markdown、code、sheet、raw bytes 还是 URL part。类型决定渲染器、权限和导出方式。

7.3 归属：artifact 必须有 owner 和 scope

同一个 artifact 可能属于一次 task、一个 session、一个 user、一个 organization，或一个 public share。ADK 的 user-scoped artifact、OpenWebUI 的 personal/shared storage、Vercel 的 user id 检查，都在处理这个问题。

7.4 版本：编辑不是覆盖，而是产生新状态

用户修改 artifact 后，如果直接覆盖原内容，就丢掉了可回滚性。Vercel 的 document versions、Open Canvas 的 contents 数组、ADK 的 version，都说明 artifact 应该天然版本化。

7.5 预览：preview 不是 publish

preview 是临时、受限、可失败的状态；publish 是稳定、可分享、有权限边界的状态。OpenClaw 的 finalizable live preview 抽象很有启发：草稿可以先显示，但最后必须显式收束。

7.6 执行：不可信代码必须进 sandbox

HTML/JS 可以用 iframe sandbox 和 CSP；Python 可以用 Pyodide worker 或远程 sandbox；完整 web app 更适合 E2B、Daytona、OpenSandbox 这类容器环境。执行层不能靠 prompt 约束。

7.7 上下文：模型不需要每轮看到完整 artifact

大工具输出和大文件应该落盘，模型上下文里保留预览、路径、版本和读取方式。Claude Code 和 Hermes 的 persisted output 说明：artifact storage 是长上下文管理的一部分。

7.8 恢复：resume 后路径和版本仍要有效

一次 agent 任务可能跨小时、跨天、跨设备。artifact 如果只能在当前内存里存在，就不适合承担交付物角色。Codex 的 rollout/thread history、Hermes checkpoint、ADK artifact service 都在保证恢复。

7.9 清理：TTL、quota、GC 是产品能力

临时媒体、sandbox 文件、preview URL、代码执行结果都会占资源。没有 TTL、quota 和 GC，artifact 系统会变成隐形存储泄漏。OpenClaw media TTL、Hermes checkpoint prune、sandbox timeout 都是必要能力。

7.10 协议：不要让 prompt 成为唯一 contract

Prompt 可以指导模型什么时候生成 artifact，但不能承担全部 runtime contract。成熟系统需要结构化事件、schema、服务接口和 UI 状态。LibreChat 的 block parser、Vercel 的 tool/data stream、A2A 的 artifact update、ADK 的 service interface，都是在把 prompt 里的意图落成协议。
