Self-Evolution 与 Agentic Training

这篇文章不把“智能体会变好”当成一句营销话术，而是把它拆成可观察的工程面： 上下文怎样被放进模型，压缩摘要为什么有训练形状，记忆和技能如何持久化，轨迹怎样变成 SFT / RL 数据，以及开源项目正在把这些环节推进到哪里。

阅读契约

本文讨论的不是某个厂商“私下究竟怎么训”的不可见内幕，而是三类可复核信号： official docs 是官方文档、论文、博客或项目页直接说清楚的事实； verified source 是公开仓库源码、README、脚本和注释能直接支持的机制； bounded inference 是从这些机制推出的合理训练流程猜测。推测会显式标注，不写成内部事实。

文章把 self-evolution 分成五层：上下文纪律、记忆/技能演化、artifact 演化、agentic RL / SFT、分布式训练基础设施。Codex、Claude Code、OpenClaw、Hermes 是前半篇的运行时主线； Agent Lightning、ART、RAGEN、Agent-R1、SWE-Gym、SWE-smith、SWE-RL、verl、DSPy、OpenEvolve、 Voyager、AgentEvolver、DisTrO/Psyche 是后半篇的训练实践主线。

证据边界：Codex 部分使用 OpenAI Codex 公开仓库 commit 02dce8e 的源码链接；OpenClaw 使用 commit e5e6cf0； Hermes 使用 commit 2dbc3bd。Claude Code 的产品事实使用官方文档； 其源码线索只引用可公开访问的 WineChord 镜像 commit 5a774a2，并按 “源码快照线索”处理。本文不声明 OpenAI、Anthropic、Nous 或任何团队的未公开训练配方。

1. 自进化到底在进化什么

“Self-evolution” 这个词太大。它可以指模型权重更新，也可以指提示词、记忆、技能、代码、工具策略、评测器、 sandbox 策略在长期使用中变好。把这些混成一个词，会让讨论失焦。

更精确的分层是：

层级 进化对象 典型实现 是否更新模型权重
上下文纪律 指令、环境、工具 schema、历史切片、压缩摘要的顺序和格式 Codex 的 contextual user fragments、AGENTS.md、prompt cache key、compaction replacement history 不更新，但可能对齐训练时格式
记忆/技能演化 长期偏好、项目事实、可复用操作说明、脚本和例子 Claude Code memory、OpenClaw workspace memory、Hermes memory provider、Codex skills 通常不更新
Artifact 演化 提示词、程序、工具包装、代码优化候选 DSPy/GEPA、OpenEvolve、Voyager skill library、AgentEvolver 的 self-questioning 可选；很多系统不更新权重
Agentic training 多轮轨迹、工具调用、环境反馈、奖励、credit assignment Agent Lightning、ART、RAGEN、Agent-R1、SWE-Gym、SWE-smith、SWE-RL、verl 通常更新 LoRA 或模型权重
分布式训练基础设施 梯度/更新包、检查点、参与者调度、低带宽同步 DisTrO、Psyche、DeMo 更新，但关注基础设施而非 agent 行为本身

这五层的关键区别是“写入面”不同：上下文纪律写入本轮请求；记忆/技能写入磁盘或长期存储； artifact 演化写入新 prompt / 新程序；agentic training 写入模型参数或 LoRA；分布式训练写入全局检查点。 只要没有分清写入面，就会把“提示词变了”“记忆变了”“模型变了”混为一谈。

2. Codex 源码里最硬的线索：训练形状

Codex 公开源码里，最值得盯的不是某个神秘训练脚本，而是模型输入的形状：哪些内容被放进请求、 什么顺序、什么时候复用 prompt cache、什么时候压缩历史，以及压缩后的 history 怎样恢复。

2.1 Contextual user fragments 的固定顺序

contextual_user_message.rs 里有一组静态注册顺序：user instructions、environment context、additional context、skill instructions、 user shell command、turn aborted、subagent notification、internal model context 等。它不是随便拼字符串， 而是把“对模型可见但不等于用户自然语言”的片段做成可识别的标准 fragment。

AGENTS.md 发现逻辑 也暴露同样的工程原则：从 project root 到当前目录收集项目规则，按路径层级拼接，不越过项目根。 这保证模型看到的项目规则是可预测的，而不是每轮随机变换的环境噪声。

2.2 Prompt cache key 是线程级稳定锚

Codex 的 ModelClient 是 session-scoped，默认把 thread_id 作为 prompt_cache_key。 后续 build_responses_request() 把 instructions、input、tools、reasoning 配置和 prompt_cache_key 一起放进 Responses API 请求。 OpenAI 的 prompt caching 文档 也强调：cache key 会和 prompt prefix 一起影响路由与缓存命中。

这里的训练含义不是“prompt cache 本身训练模型”。它更像一道工程纪律：稳定前缀让运行时输入更接近可复现样本， 也让离线分析、rollout reconstruction、错误复盘更可靠。一个训练栈如果连 runtime 输入都不稳定， 生成的轨迹数据就很难做高质量 SFT 或 RL。

2.3 Compaction 注释直接提到 “model is trained”

最强线索在 compact.rs 的 InitialContextInjection 注释里：mid-turn compaction 必须把初始上下文插到最后一个真实用户消息上方，因为模型被训练成在 mid-turn compaction 后把 compaction summary 看成 history 的最后一项。

这句话很少见，因为它不是外部观察者推测，而是源码注释直接把 runtime placement 和 model training 连接起来。 它仍然不暴露训练集生成脚本，但足够说明：压缩摘要不是 UI 层的普通提示文本，而是模型被要求识别的一种历史形状。

2.4 Replacement history 是可恢复的模型视图

Codex 的 inline compaction 流程会复制 history、加入压缩 prompt、等待 summary turn 完成，然后构造新的 replacement history。源码在 run_compact_task_inner_impl() 里把 summary 作为 CompactedItem，再调用 replace_compacted_history。 后续 build_compacted_history() 会保留最近用户消息，并把 summary 写成一条 user message。

插入初始上下文的函数 又强调：优先插在最后一个真实用户消息之前；如果只剩 summary，就让 summary 保持最后。 这就是“训练顺序对齐”的具体工程样子：不是玄学，而是替换历史的 role / order / boundary 要稳定。

合理推测：如果一个运行时显式维护 replacement history、window id、rollout reconstruction、 context fragment order，并在注释里说明模型训练过某种 compaction shape，那么训练数据管线至少需要保留 “压缩前轨迹”和“压缩后继续执行轨迹”的对应关系。否则模型无法稳定学到：看到 summary-last 的 history 后， 应该继续任务而不是重新总结、追问或忽略摘要。

3. Claude Code、OpenClaw、Hermes：记忆与轨迹的三种边界

3.1 Claude Code：记忆是 context，不是绝对命令

Anthropic 的 Claude Code memory 文档 把 memory 描述成启动时加载的上下文系统，而不是不可违背的安全策略。 公开源码快照里， getUserContext() 被 memoize，并把 CLAUDE.md / memory files 这类内容放进 user context。 主请求路径 再通过 prependUserContext(messagesForQuery, userContext) 组包。

更像“prompt-level self-evolution”的，是 memoryTypes.ts 里的 memory taxonomy：user、feedback、project、reference 四类，并明确排除可从代码、git history、CLAUDE.md 推导出来的内容。该公开镜像快照的后半段还有 eval-validated 注释 ，例如位置和标题措辞会影响 memory 使用效果。这里的证据等级是 source snapshot inference：它说明这份 memory prompt 文本被评测驱动迭代过， 不应扩大成 Anthropic 当前线上训练流程的事实。

3.2 OpenClaw：自进化写入面必须属于可信 operator 边界

OpenClaw README 把 agent workspace、AGENTS.md、SOUL.md、TOOLS.md、 skills 路径列为可注入提示文件和技能目录 来源。 但它的 security model 同时强调：模型/agent 不是可信主体，MEMORY.md 和 memory/*.md 是可信本地 operator 状态，不是多租户安全边界。

这点很重要。自进化系统如果允许模型任意写入长期记忆或技能，就等于让 prompt injection 变成长期状态污染。 OpenClaw 的 memory flush 测试还体现了更窄的写入控制： memory flush 写入被限制成 append-only 且限定目标路径 。

3.3 Hermes：轨迹压缩就是训练数据预处理

Hermes 的 trajectory_compressor.py 直接把任务写清楚：压缩已完成的 agent trajectories，让它们落在 token budget 内，同时保留训练信号质量。 它保护前几轮、保护最后几轮，只压中间，并用一条 human summary message 替换被压缩区域。

更关键的是边界 snapping： 源码注释 说不能切在 <tool_call> 和 <tool_response> 中间，否则会留下孤儿 marker， “corrupt the training trajectory”。这句话和 Codex 的 compaction 注释遥相呼应：训练样本不是一堆文本， 它有 tool pairing、role、summary role、head/tail protection 这些结构约束。

Hermes cron 路径也有边界意识： job workdir 会加载 AGENTS.md / CLAUDE.md / .cursorrules，但 cron agent 构造时 skip_memory=True ，注释理由是 cron system prompts 会污染用户表征。也就是说，自动任务和用户记忆是不同写入面。

4. Agentic Training 的基本回路

运行时线索解决“轨迹从哪里来”。训练框架解决“轨迹如何让策略变好”。一个可训练 agent 的样本不只是 prompt -> answer，而更接近： 

{
  "initial_context": "... instructions, tools, environment ...",
  "steps": [
    {"observation": "state_t", "action": "tool_call_or_text", "feedback": "tool_result", "reward": 0.0},
    {"observation": "state_t+1", "action": "patch_or_answer", "feedback": "tests", "reward": 1.0}
  ],
  "return": "G = sum_t gamma^t r_t",
  "artifacts": ["logs", "patches", "summaries", "verifier scores"]
}

这里的 \(G=\sum_t \gamma^t r_t\) 是强化学习里常见的折扣回报。对 LLM agent 来说，难点不在公式， 而在把自然语言、工具调用、环境状态、长上下文压缩、奖励归因统一成可训练的 token/action 边界。

4.1 Agent Lightning：训练与 agent 执行解耦

Microsoft 的 Agent Lightning 官方介绍 和 论文 主张 Training-Agent Disaggregation：agent 继续按原框架运行，tracer 把 prompt、工具调用、奖励等事件变成结构化 spans， trainer/algorithm 再消费这些 traces。README 的架构段也写到：runners 和 tracers 发 spans， LightningStore 同步，algorithm 读取 spans 并产出 refined prompt 或 policy weights。

这条路线很有工业感：它不要求把所有 agent 重写成某个 RL 环境，而是在 agent 外面包观测和训练层。 对已有 LangChain、OpenAI Agents SDK、AutoGen、CrewAI 这类系统，这比推倒重来现实得多。

4.2 ART：把 GRPO 封装成 agent 应用可调用的训练服务

ART 自称 Agent Reinforcement Trainer， README 说它用 GRPO 训练 multi-step agents。它的训练循环非常直接： agent 执行 rollouts，消息存进 Trajectory，rollout 结束后代码给 trajectory 赋 reward， 再把同一 scenario 的 trajectories 分组送进 trainer。

ART 的优势是工程入口低：写一个 rollout function、定义 scenario、给 reward，就能把 agent 应用接入训练。 局限也明显：reward 质量和 scenario 覆盖决定上限。它适合快速把“应用任务”变成训练任务，但需要严肃评测和防 reward hacking。

4.3 RAGEN 与 Agent-R1：把多轮 agent 明确建成 MDP

RAGEN 的 StarPO 把 state、thinking、action、reward 组成 trajectory-level optimization。RAGEN-2 又把 template collapse 拆成 \(H(Z|X)\) 和 \(I(X;Z)\) 两个维度：同一个输入内部看似多样， 不代表不同输入之间真的有区分度。它的价值不只是训练，而是诊断 agent RL 为什么“看起来在想、其实在套模板”。

Agent-R1 则更强调 step-level MDP： 每一步记录 observation、action、feedback、reward、done 和 next observation。它把 context management 放进训练底座：历史可以追加、截断、摘要、重写或增强，但这些变化都要和 step 边界对齐。

4.4 SWE-Gym / SWE-smith / SWE-RL：软件工程训练的可验证环境

软件工程 agent 的训练难点是 reward 不该只看文本相似度。真实仓库里，补丁能否通过测试、是否解决 issue、 是否破坏已有行为，才是高价值信号。SWE-Gym 提供真实 Python repo 任务、可执行环境和测试验证；SWE-smith 把任意 GitHub repo 变成 SWE-gym，并合成大量任务；SWE-RL 用开放软件演化数据和 rule-based rewards 训练代码编辑能力。

这类系统说明一个更一般的原则：agentic training 最缺的常常不是算法名，而是可重复环境和可信 verifier。 没有环境，RL 只是对文本格式打分；有了环境，reward 才能连接真实结果。

5. 开源实践排序：流行度和能力必须分开

排序快照日期：2026-06-16。GitHub stars/forks、PyPI 或项目自述里的下载信号、论文/项目页、下游案例和社区讨论 都只作为采用度代理，且这些指标随时间快速变化，本文不把实时数值写成固定事实。能力排序是 editorial ranking， 不是可复现实验分数；rubric 是六项定性标准：多轮 MDP 表达、轨迹/trace 质量、reward 与 verifier、 credit assignment、训练/推理解耦、复现和部署成本。等级含义是：S 表示能力覆盖最完整，A 表示能力强但仍需补足某些工程面， B 表示更偏单一层面或 artifact 演化。

6. 不更新权重的自进化：prompt、skill、code artifact

不是所有 self-evolution 都要 RL。很多实际系统先做更便宜、更可控的 artifact evolution。 这类路线的共同点是：模型负责提出候选，环境/测试/评测器负责筛选，持久化层保存胜者。

6.1 DSPy / GEPA：把 prompt 当成可优化参数

DSPy 的核心口号是 “programming, not prompting”。它把 LM 调用声明成程序模块，再用优化器搜索 instructions、demonstrations 或更复杂的 prompt 结构。GEPA 进一步把 reflective prompt evolution 做成优化过程。 这类系统不会自动让底层模型参数变聪明，但会让当前任务上的 agent program 变得更可靠。

6.2 OpenEvolve：LLM 做 mutation，评测器做 selection

OpenEvolve 是更偏程序演化的路线：LLM 生成候选代码，evaluator 跑测试或 benchmark，数据库保留高质量和多样性候选。 它像把 AlphaEvolve 类思路开源化：自进化发生在代码空间，不直接发生在模型权重上。

6.3 Voyager 与 AgentEvolver：技能库和经验管理

Voyager 在 Minecraft 里通过 automatic curriculum、 executable skill library、environment feedback 和 self-verification 积累技能。它的论文路线很早， 但今天看仍然是 self-evolution 的清晰原型：模型不更新，技能库增长。

AgentEvolver 则把自进化拆成 self-questioning、 self-navigating、self-attributing：自己生成任务、复用经验引导探索、对长轨迹做归因。这已经接近 “artifact evolution + agentic RL” 的交叉地带。

7. Hermes / Nous 线索：去中心化训练不是玄学，但也不是 agent 训练万能解

Nous 的 DisTrO README 把目标写成 Distributed Training Over-The-Internet，声称通过低延迟分布式优化器把 inter-GPU communication 降低三到四个数量级。Nous 的 Psyche 文章则把这个方向扩展到去中心化训练网络：更多低利用率硬件参与训练，通过压缩更新和协调机制同步。

这和 Hermes-agent 的关系不是“用 Hermes 就自动去中心化训练”，而是生态方向一致：Hermes 提供 agent runtime、 memory、trajectory compressor；DisTrO/Psyche 处理大规模训练基础设施。把两者接起来时，最难的仍然是数据治理： 哪些轨迹可训练、如何脱敏、如何评分、如何防止恶意参与者污染梯度。

8. 从这些线索反推一个可信训练流程

下面是一个 bounded inference，不是任何厂商的内部配方。 它只是把上面所有公开线索连成一个工程上合理的 agentic training pipeline：

  1. 采集轨迹：保存模型输入、工具 schema、tool call、tool result、审批结果、错误、环境上下文、文件 patch、 测试输出和 token usage。Codex 的 history manager / rollout reconstruction、Hermes trajectory compressor、 OpenClaw trajectory flush 都说明这类轨迹是重要资产。
  2. 结构修复：保证 tool call / tool response 配对完整，去掉 transcript-only UI 项，修复空 assistant turn， 保留 provider 可接受的 message role 顺序。Hermes “corrupt training trajectory” 注释就是这个阶段的典型风险。
  3. 上下文归一：把 developer / user / environment / project docs / skills / tools 放进稳定顺序； 把动态环境放在明确 fragment 中；把不该训练的本地路径、secret、私人上下文剥离。
  4. 压缩与 continuation 样本：为长轨迹生成 summary，保留压缩前后继续完成任务的对应关系。 Codex 源码里“模型训练成 summary-last”的注释说明这个阶段的格式并非随意。
  5. 奖励与 verifier：软件工程任务跑测试，搜索任务核对答案，游戏/环境任务读 reward，开放式任务用 critic 或 RULER。 只有可验证 reward 才能支撑 RL；弱 reward 更适合 SFT 或 rejection sampling。
  6. 训练更新：低成本从 SFT / rejection sampling 开始；多轮 agent 行为再接 PPO、GRPO、StepPO、RLOO。 对已有 agent，Agent Lightning 式 trace 解耦更现实；对新研究环境，Agent-R1 / RAGEN 式 MDP 建模更干净。
  7. 门禁回放：每次训练或 prompt/skill 变更都跑 eval replay，检查 reward hacking、template collapse、memory drift、 sandbox leakage、benchmark overfit。

这条流程解释了为什么“environment context 放哪里”“summary 是 user role 还是 system role”“AGENTS.md 怎么排序” 会和训练有关：只要运行时轨迹会进入训练或评测，格式就是数据 schema；schema 变了，模型学到的 continuation 习惯就可能失配。

9. 最容易踩的六个坑

9.1 Context corruption

把不可信外部内容放进高优先级上下文，或把动态噪声放进稳定 cache prefix，会让模型把 metadata 当指令， 也会让训练样本带毒。修复方式是明确 fragment、role、source、trust boundary。

9.2 Reward hacking

RAGEN 的 reward hacking 案例文件 展示过“模型输出看似完成、实际利用格式/终止条件骗 reward”的问题。软件工程里也类似： 如果 reward 只看 diff 相似度，模型可能学会贴近 oracle 格式，而不是修复问题。

9.3 Template collapse

低 entropy 不一定坏，高 entropy 也不一定好。RAGEN-2 的 \(I(X;Z)\) 和 \(H(Z|X)\) 提醒我们： reasoning 必须随输入变化，否则只是“多样化模板”。

9.4 Memory drift

Claude Code 的 memory prompt 快照里反复强调：memory 可能过期，涉及文件/函数/flag 的记忆要重新 grep。 自进化系统如果不淘汰旧记忆，长期效果会变差。

9.5 Sandbox leakage

OpenClaw security model 把 memory 和 skills 视为可信 operator 状态，说明这不是模型能任意写的区域。 一旦把 untrusted channel 写入长期文件，再由 memory search 注入未来上下文，就形成持久污染链。

9.6 Benchmark overfit

SWE 环境越标准，越容易形成 benchmark-specific 策略。需要 held-out repos、真实 issue、不同 harness、best-of-n critic 之外的人工抽检，才能判断 agent 是否真正变强。

10. 实战选择：今天应该怎么用

目标 首选路线 不要一开始就做的事
让现有 agent 在真实任务上变好 先接 trace、reward、eval replay；优先看 Agent Lightning 或 ART。 不要先改模型权重而没有环境/verifier。
训练代码修复 agent SWE-Gym / SWE-smith / SWE-RL + OpenHands/SWE-agent scaffold + 测试 reward。 不要只用文本相似度 reward 代表修复成功。
研究多轮 RL 算法 Agent-R1 或 RAGEN；明确 step / trajectory / reward / context manager。 不要把完整多轮历史当单条平铺 prompt 就结束。
低成本做自进化产品能力 DSPy/GEPA 优化 prompt，OpenEvolve 优化代码 artifact，技能库加版本和 eval。 不要让模型无门禁写 memory / skills。
构建长期本地 agent 学习 OpenClaw/Hermes：记忆、skills、cron、tool policy、trajectory compression 分离。 不要把用户记忆、自动任务记忆、训练轨迹混在一个桶。
探索去中心化训练 先理解 DisTrO/Psyche 的同步和压缩，再解决数据治理和评测门禁。 不要把“能分布式训练”误读为“agent 数据可信”。

一句话结论：Agent 的自进化不是一个功能按钮，而是一条数据供应链。 上游是运行时的上下文形状和轨迹质量，中游是压缩、记忆、技能和 reward， 下游才是 SFT/RL/分布式训练。 如果上游 schema 不稳，下游算法越强，越可能把坏习惯放大。
